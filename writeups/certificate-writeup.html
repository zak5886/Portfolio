Certificate

HardWindows

Certificate is a Hard-difficulty Windows Active Directory box centered on a school/e-learning web app that accepts assignment uploads, including zip archives. Two independent filename-handling tricks (a null byte hidden in a zip entry, and stacking two zip archives together) are used to smuggle a PHP webshell past an allow-list filter. From there the chain runs through a leaked DB hash, a Kerberos authentication recovered from a stray packet capture, an ESC3 abuse of the AD CS environment, a SeManageVolumePrivilege arbitrary-file-read trick, and finally a Golden Certificate forgery against an exfiltrated CA private key to decrypt an EFS-protected root flag as Administrator.

PHASE 1

Reconnaissance

A large open-port footprint — Kerberos, LDAP, SMB, the works — immediately marks this as a Windows Domain Controller rather than a standalone host.

Full-range port scan

Why21 open TCP ports, heavily weighted toward classic AD/DC services (Kerberos 88, LDAP 389/3268, SMB 445, WinRM 5985).

nmap -p- --min-rate 10000 <TARGET>
nmap -p53,80,88,135,139,389,445,464,593,636,3268,3269,5985,9389 -sCV <TARGET>
Domain: certificate.htb0., Site: Default-First-Site-Name
80/tcp open http Apache 2.4.58 (Win64) OpenSSL/3.1.3 PHP/8.0.30

NextResolve the domain and DC hostname, then start with the one port that isn't AD infrastructure: the web app on 80.

Resolve the domain controller

WhyAn SMB-aware enumeration tool can resolve and write the domain/hostname mappings directly, saving a manual LDAP/SMB-banner lookup.

netexec smb <TARGET> --generate-hosts-file hosts
10.10.11.71  DC01.certificate.htb certificate.htb DC01

NextBrowse the web application — an online learning platform — to map out its functionality before touching anything authenticated.

Map the web application

WhyThe site is a course-enrollment platform for an online school. Registration is open to both student and teacher accounts (teacher accounts need separate activation). Once authenticated, course pages expose quiz/assignment upload forms that accept documents and zip archives — the feature that ends up mattering.

PHASE 2

Foothold — Defeating the Upload Filter

The quiz/assignment upload accepts documents or zips containing documents. Getting a PHP webshell past this requires understanding three independent checks stacked together: file extension, declared Content-Type, and file-content magic bytes — and finding where the zip-handling logic disagrees with the direct-upload logic.

Probe the filter layer by layer

WhyTesting a .php upload directly gets blocked on Content-Type; the same file inside a zip gets blocked at the extension-inside-the-archive check instead; and a file whose raw bytes contain obvious PHP code gets blocked even when disguised with a .pdf extension — meaning there's a magic-byte or content-signature check layered on top of the extension check.

NextHide a PHP payload inside an otherwise-valid PDF by embedding it in an existing content stream, so the file still passes as a legitimate PDF by signature while carrying executable PHP.

Embed a PHP payload inside a genuine PDF stream

WhyEditing a real PDF's internal stream object to splice in a PHP one-liner keeps the file's magic bytes and overall structure intact (the PDF itself won't render correctly, but it still validates as a PDF to any signature check), while giving the uploaded content actual PHP to execute once interpreted with the right extension.

NextThis solves the content-signature problem, but the file still needs a .php extension to actually execute — and the allow-list rejects that extension directly. A null-byte trick in the zip entry name is the way around it.

PHASE 3

Webshell via Null-Byte Zip Entry

PHP's ZipArchive class and the filesystem can disagree about where a filename ends when a null byte sits in the middle of it — exactly the kind of parser-differential bug that defeats allow-list filters.

Insert a null byte into the zip entry filename

WhyRenaming the crafted PDF+PHP payload to something like shell.php..pdf, zipping it, then hex-editing the two period bytes in the zip's filename metadata to null bytes produces an entry that PHP's ZipArchive reads as ending in .pdf (because it stops at the embedded null when building the display string) while the extraction/write logic underneath actually writes the file to disk as shell.php.

php -a
$zip = new ZipArchive();
$zip->open('nulls.zip');
echo $zip->getNameIndex(0);  // "embedded.php\x00.pdf" -> displays as "embedded.php .pdf"

NextUpload the crafted archive and confirm the filter passes it, then locate where the resulting file actually landed on disk.

Upload and trigger the webshell

WhyThe filter accepts the archive (it sees a .pdf-terminated name), but the file on disk is written as embedded.php — directly executable.

NextA second, independent technique (stacked zip archives) achieves the same outcome by exploiting a different parser disagreement, and is documented here for completeness since it's a broadly useful upload-bypass pattern beyond this one box.

PHASE 4

Alternate Technique — Stacked Zip Archives

Concatenating two complete zip files back-to-back produces a single file that different parsers read completely differently — command-line unzip sees only the second archive's contents, while PHP's ZipArchive sees only the first.

Build two zips and concatenate them

WhyThe first archive contains a legitimate, filter-passing PDF; the second contains the PHP webshell (again disguised inside a valid-looking PDF stream). Concatenating them with cat produces one file that PHP's own validation logic inspects as just the first (benign) archive.

zip nice.zip dummy.pdf
zip evil.zip shell.php
cat nice.zip evil.zip > combined.zip

NextUpload the combined archive — the server-side validation checks only the first archive's contents, but the extraction step that actually writes files to disk unpacks the second archive instead.

Confirm the webshell and get code execution

WhyThe validation/extraction mismatch means the webshell from the second archive lands on disk even though it was never inspected by the filter.

NextWith a PHP webshell confirmed working by either method, deliver a PowerShell reverse shell as the command payload.

Get an interactive shell

WhyA standard base64-encoded PowerShell reverse-shell one-liner, passed as the webshell's command parameter, calls back to a listener.

PS C:\xampp\htdocs\certificate.htb\static\uploads\...>

NextThis lands as xamppuser — the local service account running the XAMPP stack, not a domain account. Enumerate the web app's own database for credentials that might lead further.

PHASE 5

Shell as Sara.B — Credential Recovery from the Web DB

The web app's own MySQL database, reachable with credentials pulled straight from its PHP config file, holds a password hash that turns out to belong to a real domain user with an administrative role on the site.

Read the database connection config

Whydb.php in the web root contains plaintext MySQL credentials for the application's own database user.

NextUse those credentials with the bundled mysql.exe binary to dump the users table.

Dump the application's users table

WhyThe users table holds bcrypt password hashes for every registered account — both legitimate pre-existing accounts and the one just self-registered during recon.

\xampp\mysql\bin\mysql.exe -u certificate_webapp_user -p'<pw>' -e "use certificate_webapp_db; select username,password from users;"

NextCrack the pre-existing hashes offline with hashcat, ignoring any accounts created during testing.

Crack the recovered hashes

Whybcrypt at this cost factor cracks fast for weak passwords; one hash (belonging to sara.b, marked admin in the app's role column) breaks almost immediately against a standard wordlist, while the rest hold.

hashcat web.hashes /path/rockyou.txt --user -m 3200
sara.b:$2y$04$...:Blink182

NextTest whether sara.b reused this web-app password for her actual domain account.

Confirm domain password reuse and connect

WhyThe cracked password works directly against SMB and WinRM for the real domain account — a classic web-app to domain-account credential-reuse chain.

netexec smb dc01.certificate.htb -u sara.b -p Blink182
evil-winrm-py -i dc01.certificate.htb -u sara.b -p Blink182

NextWith a domain foothold established, collect BloodHound data to map the real attack paths through the AD environment.

PHASE 6

Shell as Lion.SK — Recon via BloodHound and a Stray PCAP

BloodHound surfaces the next hop almost immediately once real domain credentials are available, and a forgotten packet capture in a user's own Documents folder hands over the credential needed to use it.

Collect and analyze BloodHound data

WhyCollection confirms Sara.B holds broad GenericAll rights over several accounts (the result of an over-permissioned group membership), which would normally allow directly resetting another user's password — though that path gets patched mid-engagement in this environment, redirecting to a PCAP found in her own home directory instead.

netexec ldap dc01.certificate.htb -u sara.b -p Blink182 --bloodhound -c ALL --dns-server <TARGET>

NextCheck Sara.B's own Documents folder for anything left behind from prior troubleshooting — a workstation folder containing a packet capture turns out to be the real path forward.

Recover a leftover packet capture

WhyA WS-01 folder contains a short note describing an SMB share access issue, plus the packet capture taken while diagnosing it — exactly the kind of artifact a helpdesk ticket leaves behind and then nobody deletes.

NextOpen the PCAP and look for any authentication traffic that could be converted into a crackable hash.

Extract a Kerberos pre-auth hash from the capture

WhyFiltering for Kerberos traffic in the capture surfaces an AS-REQ for user Lion.SK carrying an encrypted timestamp in its pre-authentication data — enough to reconstruct a crackable $krb5pa$-format hash by hand from the five required fields (encryption type, username, realm, and the encrypted timestamp itself), or by running a purpose-built parser against the file directly.

$krb5pa$18$Lion.SK$CERTIFICATE.HTB$23f5159fa1c66ed7b0e561543eba6c01...

NextCrack the Kerberos pre-auth hash offline.

Crack the Kerberos hash

WhyHashcat auto-detects the Kerberos 5 etype 18 pre-auth hash mode and breaks it quickly against a standard wordlist.

hashcat lion.hash /path/rockyou.txt
$krb5pa$...:!QAZ2wsx

NextVerify the recovered password against SMB/WinRM for Lion.SK, then connect.

Authenticate as Lion.SK

WhyThe cracked password works directly for both SMB and WinRM authentication, giving a genuine second domain foothold.

evil-winrm-py -i DC01.certificate.htb -u Lion.SK -p '!QAZ2wsx'
PS C:\Users\Lion.SK> cat user.txt
PHASE 7

Shell as ryan.k — Abusing ADCS ESC3

Lion.SK's group membership points straight at the Certificate Authority: Domain CRA (Certificate Registration Authority) Managers. A fresh BloodHound collection with Lion.SK's own credentials confirms an enrollment path on a vulnerable certificate template.

ESC3 — Certificate Request Agent Template Abuse

The Delegated-CRA template is configured with the Certificate Request Agent Extended Key Usage and is enrollable by the Domain CRA Managers group. A certificate issued from this template lets its holder act as an enrollment agent — requesting certificates on behalf of other users from a separate, client-authentication-capable template, effectively letting a low-privileged group mint identity certificates for anyone whose chosen template doesn't block agent-based enrollment.

Enumerate AD CS with Certipy

WhyCertipy's find -vulnerable flags the Delegated-CRA template directly, confirming the ESC3 classification and showing exactly which group can enroll in it.

certipy find -u Lion.SK -p '!QAZ2wsx' -target certificate.htb -vulnerable -stdout

NextRequest an enrollment-agent certificate as Lion.SK first, which will be used to request certificates on behalf of other users.

Obtain an enrollment agent certificate

WhyThis certificate is what lets Lion.SK act as an agent for a second, on-behalf-of request later.

certipy req -u Lion.SK -p '!QAZ2wsx' -target certificate.htb -ca 'Certificate-LTD-CA' -template Delegated-CRA

NextIdentify a second template that Domain Users can enroll in and that supports client authentication, since that's what's needed for an on-behalf-of request to produce a usable logon certificate.

Pick a target user and template

WhyA first attempt to request a certificate on behalf of Administrator fails because that template requires an email subject the Administrator account doesn't have set. Reviewing other users with usable templates and interesting group memberships, Ryan.K stands out as a member of Domain Storage Managers — a group with direct volume-level access rights that's worth pursuing.

NextRequest a certificate on Ryan.K's behalf using the enrollment-agent certificate obtained for Lion.SK.

Request a certificate on Ryan.K's behalf and authenticate

WhyThe on-behalf-of request succeeds this time (Ryan.K's account has the required subject email set), yielding a certificate usable for Kerberos authentication and NTLM hash recovery.

certipy req -u Lion.SK -p '!QAZ2wsx' -target certificate.htb -ca 'Certificate-LTD-CA' -template SignedUser -on-behalf-of 'CERTIFICATE\\ryan.k' -pfx lion.sk.pfx
certipy auth -pfx ryan.k.pfx -dc-ip <TARGET>
Got hash for 'ryan.k@certificate.htb': ...b1bc3d70e70f4f36b1509a65ae1a2ae6

NextConnect as Ryan.K and check what the Domain Storage Managers membership actually grants.

PHASE 8

Shell as Administrator — SeManageVolumePrivilege and a Golden Certificate

Ryan.K's privilege set includes SeManageVolumePrivilege — an underappreciated token privilege that effectively grants raw disk access and can be abused to bypass NTFS ACLs entirely.

SeManageVolumePrivilege Abuse

This privilege is meant for legitimate volume-maintenance tasks (defragmentation, dismounting), but holding it grants low-level FSCTL access to the volume that a public tool (SeManageVolumeExploit) abuses to mass-rewrite NTFS ACL entries, replacing the Administrators group's access-control entries with the regular Users group — effectively opening every file on the volume to the current, non-administrative user.

Run the volume-privilege ACL rewrite

WhyA single execution rewrites hundreds of ACL entries across the volume, granting file read access that should never have been available to a non-admin account.

SeManageVolumeExploit.exe
Entries changed: 842
DONE

NextAttempt to read root.txt directly from the Administrator desktop now that ACLs have been rewritten.

Hit the EFS wall

WhyThe flag file is readable at the filesystem-permission level now, but still refuses to open — it's encrypted with EFS (Windows' file-level encryption), which NTFS ACL bypass alone can't defeat; EFS needs the right private key, not just file access.

NextA Golden Certificate attack — compromising the CA's own private key — can forge a certificate for any user, including Administrator, and recovering the matching NTLM hash provides a path to a full Administrator logon rather than EFS key recovery directly.

Export the CA's private key

WhyWith local admin-equivalent file access (from the ACL rewrite), the CA's own certificate and private key can be exported directly from the local certificate store using the CA's known serial number.

certutil -exportPFX <ca-serial> .\ca.pfx

NextDownload the exported CA key pair and use it offline to forge an arbitrary certificate.

Forge an Administrator certificate

WhyPossessing the CA's private key means being able to sign any certificate the CA would ever issue — including one asserting an Administrator UPN that was never legitimately requested through the CA's normal enrollment process.

certipy forge -ca-pfx ca.pfx -upn Administrator@certificate.htb -subject 'CN=ADMINISTRATOR,CN=USERS,DC=CERTIFICATE,DC=HTB'

NextAuthenticate with the forged certificate to obtain both a Kerberos ticket and the Administrator NTLM hash.

Authenticate with the forged certificate

WhyCertipy's PKINIT-based authentication against the forged certificate returns a valid TGT and, via U2U, the Administrator account's NTLM hash — either is sufficient for a full logon.

certipy auth -pfx administrator_forged.pfx -dc-ip <TARGET>
Got hash for 'administrator@certificate.htb': ...d804304519bf0143c14cbf1c024408c6

NextUse the recovered NTLM hash to open an Administrator shell and read the root flag.

Shell as Administrator

WhyPass-the-hash with the recovered NTLM hash grants a full Administrator session, which this time reads the EFS-protected flag cleanly because the session itself now holds Administrator's own decryption context.

evil-winrm -i DC01.certificate.htb -u administrator -H d804304519bf0143c14cbf1c024408c6
*Evil-WinRM* PS C:\Users\Administrator\desktop> cat root.txt

Key Takeaways

  • Upload allow-lists must be enforced consistently at every layer that touches the file — extension check, Content-Type check, and magic-byte check are each individually bypassable, and an archive-extraction step that disagrees with the validation step is enough to defeat all three at once.
  • Any PCAP, log, or troubleshooting artifact left in a user-writable location is effectively a credential-disclosure risk — Kerberos pre-authentication data is crackable offline exactly like an NTLM hash once captured.
  • A Certificate Request Agent (ESC3) template should be restricted as tightly as domain admin rights — it effectively lets its holder issue identity certificates for any enrollable user, turning a narrow group membership into a path toward much higher-privileged accounts.
  • SeManageVolumePrivilege is frequently overlooked in privilege reviews but is functionally equivalent to raw disk access; it should never be assigned to a non-administrative account or group.
  • Compromise of a CA’s private key is catastrophic regardless of any other control in place — a Golden Certificate attack forges trust for the entire PKI, which is why CA private keys need hardware-backed protection (HSM) and the strictest possible access controls.
