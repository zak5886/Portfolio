📥L1 Escalation IntakePROCESS

When L1 escalates, your first job is to validate their assessment — not just accept it. Re-examine the evidence independently.

Intake Checklist

  • Read full L1 ticket — understand what they found and their conclusion
  • Verify the SIEM alert independently — pull raw logs yourself
  • Confirm IOC enrichment is accurate and complete
  • Check for correlated events L1 may have missed (±6 hours, same user/host)
  • Re-assess severity — do you agree with L1's classification?
  • Identify any gaps in L1's investigation
  • Acknowledge receipt to L1 — give estimated response timeline
  • Assign ticket to yourself and update status

L1 Intake Questions

QuestionWhy It Matters
Is this actually malicious or could it be authorized activity?L1 may misclassify authorized pen test / red team / admin tasks
What is the blast radius? How many assets are affected?L1 often focuses on the single alerted asset
Has this user/host been involved in prior incidents?Repeat compromises suggest incomplete remediation
What is the full timeline — first event, not just alert trigger?Alert fires after attacker is already active
Is there evidence of lateral movement to other hosts?Critical for blast radius assessment
Was any data accessed or exfiltrated?Changes incident severity and legal obligations

Escalation Validation Workflow

1
Read L1 Ticket
Understand their findings. Note what they checked and what they missed. Do not just inherit their conclusion.
2
Independent SIEM Query
Re-run your own search. Expand time window. Look for precursor events (recon, delivery, initial access before L1's alert time).
3
Full IOC Expansion
From L1's IOCs, pivot: find more related IPs, domains, hashes using threat intel. Expand the scope of known bad indicators.
4
Blast Radius Assessment
Search all internal assets for connections to/from the identified IOCs. How many hosts were exposed? Who else logged in from the same compromised account?
5
Severity Confirmation or Upgrade
Confirm L1's severity or upgrade it. Update ticket. If P1 — activate IR immediately.

🔬Investigation MethodologyL2 CORE

L2 Investigation Framework: PICERL

Preparation
Tools ready, runbooks current, comms channels open, access verified
Identification
Confirm true positive, scope blast radius, identify attack type
Containment
Short-term isolation + long-term containment strategy
Eradication
Remove malware, close access paths, patch vulnerabilities
Recovery
Restore systems, verify clean state, monitor closely
Lessons Learned
Root cause analysis, detection gaps, playbook improvements

Attack Reconstruction Approach

1
Establish the Timeline
Work backwards from the alert. Find the earliest attacker footprint. Build chronological timeline of all attacker actions.
2
Map to MITRE ATT&CK
Identify every TTP observed. Map each observed behavior to a technique ID. This drives detection gap analysis.
3
Pivot on Every IOC
Each IOC is a pivot point. From a malicious IP → find all hosts that connected to it. From a hash → find all hosts with that file. From a user → find all systems accessed.
4
Determine Initial Access Vector
How did the attacker get in? Phishing? Exposed service? Credential reuse? Supply chain? This is critical for prevention.
5
Identify Persistence Mechanisms
What did the attacker do to maintain access? All persistence mechanisms must be identified and removed.
6
Data Impact Assessment
What data was accessed, modified, or exfiltrated? Required for legal, compliance, and breach notification.

Get-WinEvent -FilterHashtable @{LogName='Security'; Id=4688; StartTime=(Get-Date).AddHours(-24)} |
  ForEach-Object {
    $xml = [xml]$_.ToXml()
    [PSCustomObject]@{
      Time = $_.TimeCreated
      User = $xml.Event.EventData.Data | Where-Object{$_.Name -eq 'SubjectUserName'} | Select-Object -Exp '#text'
      Process = $xml.Event.EventData.Data | Where-Object{$_.Name -eq 'NewProcessName'} | Select-Object -Exp '#text'
      CommandLine = $xml.Event.EventData.Data | Where-Object{$_.Name -eq 'CommandLine'} | Select-Object -Exp '#text'
    }
  } | Export-Csv processes.csv -NoTypeInformation

Sysmon Log Analysis

POWERSHELL
# Sysmon Event IDs reference:
# 1  = Process Create
# 2  = File creation time changed
# 3  = Network connection
# 7  = Image loaded (DLL)
# 8  = CreateRemoteThread (process injection!)
# 10 = ProcessAccess (LSASS dumps)
# 11 = FileCreate
# 12/13 = Registry events
# 15 = FileCreateStreamHash (ADS)
# 22 = DNS query
# 23 = File Delete

# Find process injections (CreateRemoteThread)
Get-WinEvent -FilterHashtable @{LogName='Microsoft-Windows-Sysmon/Operational'; Id=8} |
  Select-Object TimeCreated,
    @{N='SourceImage';E={([xml]$_.ToXml()).Event.EventData.Data | Where-Object{$_.Name -eq 'SourceImage'} | Select-Object -Exp '#text'}},
    @{N='TargetImage';E={([xml]$_.ToXml()).Event.EventData.Data | Where-Object{$_.Name -eq 'TargetImage'} | Select-Object -Exp '#text'}}

# DNS queries by process (detect DNS tunneling or malware C2)
Get-WinEvent -FilterHashtable @{LogName='Microsoft-Windows-Sysmon/Operational'; Id=22} |
  ForEach-Object {
    $xml = [xml]$_.ToXml()
    [PSCustomObject]@{
      Time    = $_.TimeCreated
      Process = $xml.Event.EventData.Data | Where-Object{$_.Name -eq 'Image'} | Select-Object -Exp '#text'
      Query   = $xml.Event.EventData.Data | Where-Object{$_.Name -eq 'QueryName'} | Select-Object -Exp '#text'
    }
  } | Where-Object { $_.Process -notlike "*svchost*" }

🔗Event CorrelationANALYSIS

Correlation Techniques

Correlation is about connecting seemingly unrelated events to reveal an attack chain. Never analyze events in isolation.

Temporal Correlation

SPLUNK SPL
# Find all events involving a user within ±30 min of a suspicious event
index=* user="jsmith"
| where _time >= (relative_time(strptime("2024-01-15 14:30:00","%Y-%m-%d %H:%M:%S"),"-30m"))
  AND _time <= (relative_time(strptime("2024-01-15 14:30:00","%Y-%m-%d %H:%M:%S"),"+30m"))
| table _time, index, sourcetype, host, src_ip, dest_ip, process, command, action
| sort _time

# Cross-source correlation: same IP in firewall + auth + proxy logs
index=firewall OR index=auth OR index=proxy src_ip="192.168.1.50"
| eval source_type=case(index="firewall","FW",index="auth","AUTH",index="proxy","PROXY",1=1,"OTHER")
| table _time, source_type, src_ip, dest_ip, user, action, url
| sort _time

Entity-Based Correlation

SENTINEL KQL
// Full user activity timeline — correlate across all tables
let TargetUser = "jsmith@company.com";
let TimeRange = 24h;
union
(SigninLogs | where TimeGenerated > ago(TimeRange) | where UserPrincipalName =~ TargetUser
 | project TimeGenerated, Activity="SignIn", Details=strcat(IPAddress," - ",AppDisplayName," - ",ResultDescription)),
(AuditLogs | where TimeGenerated > ago(TimeRange) | where InitiatedBy has TargetUser
 | project TimeGenerated, Activity="AuditAction", Details=OperationName),
(DeviceProcessEvents | where TimeGenerated > ago(TimeRange) | where AccountName =~ split(TargetUser,"@")[0]
 | project TimeGenerated, Activity="ProcessExec", Details=strcat(DeviceName," - ",FileName," - ",ProcessCommandLine)),
(DeviceNetworkEvents | where TimeGenerated > ago(TimeRange) | where InitiatingProcessAccountName =~ split(TargetUser,"@")[0]
 | project TimeGenerated, Activity="NetworkConn", Details=strcat(DeviceName," - ",RemoteIP,":",RemotePort))
| order by TimeGenerated asc

IOC-Based Correlation

SPLUNK SPL
# Search ALL indexes for a list of known bad IPs
index=* [inputlookup malicious_ips.csv | rename ip as src_ip | fields src_ip]
  OR [inputlookup malicious_ips.csv | rename ip as dest_ip | fields dest_ip]
| table _time, index, sourcetype, host, user, src_ip, dest_ip, action
| sort _time

# Find all hosts that communicated with C2 infrastructure
index=network (dest_ip="10.0.0.1" OR dest_ip="185.234.1.1" OR dest_domain="evil-c2.com")
| stats values(src_ip) as affected_hosts, count by dest_ip
| eval affected_count = mvcount(affected_hosts)

⛓️Attack Chain AnalysisMITRE

Attack Chain Reconstruction Template

T+0:00 — INITIAL ACCESS
How did attacker get in?
Phishing email / exploit / valid credentials / supply chain. Check email logs, VPN logs, web access logs.
T+0:xx — EXECUTION
What ran on the victim host?
PowerShell, VBScript, Office macro, compiled binary. Check process creation logs, Sysmon event 1.
T+0:xx — PERSISTENCE
How did attacker ensure return access?
Scheduled task, registry run key, new service, WMI subscription, startup folder, modified SSH keys.
T+0:xx — PRIVILEGE ESCALATION
How did attacker gain higher privileges?
Token impersonation, exploit, UAC bypass, sudo abuse. Check for admin/SYSTEM processes spawned from low-priv context.
T+0:xx — DEFENSE EVASION
How did attacker avoid detection?
Log clearing (Event 1102), AV disabling, LOLBAS, DLL side-loading, process hollowing, timestomping.
T+0:xx — CREDENTIAL ACCESS
What credentials were stolen?
LSASS dump, SAM/NTDS.dit, keylogger, browser credentials, credential vaults.
T+0:xx — LATERAL MOVEMENT
Where did attacker spread?
PsExec, WMI, RDP, Pass-the-Hash, Pass-the-Ticket. Check auth logs from compromised host to others.
T+0:xx — EXFILTRATION / IMPACT
What was the attacker's goal?
Data theft (check DLP/proxy), ransomware (file encryption events), destructive action (file deletion, wiper).

PE Analysis with Python

PYTHON
import pefile
import hashlib

pe = pefile.PE("sample.exe")

# Compile timestamp
import datetime
print("Compile time:", datetime.datetime.fromtimestamp(pe.FILE_HEADER.TimeDateStamp))

# Imported functions (suspicious imports)
suspicious_imports = [
    'CreateRemoteThread','VirtualAllocEx','WriteProcessMemory',  # Injection
    'CryptEncrypt','CryptDecrypt',                                # Encryption
    'RegSetValueEx','RegCreateKeyEx',                            # Persistence
    'InternetOpen','HttpSendRequest','URLDownloadToFile',        # Network
    'IsDebuggerPresent','CheckRemoteDebuggerPresent',            # Anti-debug
]

print("\n[!] Suspicious Imports Found:")
for entry in pe.DIRECTORY_ENTRY_IMPORT:
    for imp in entry.imports:
        if imp.name and imp.name.decode() in suspicious_imports:
            print(f"  {entry.dll.decode()} -> {imp.name.decode()}")

# Sections entropy (high entropy = packed/encrypted)
print("\n[*] Section Entropy:")
for section in pe.sections:
    entropy = section.get_entropy()
    flag = " ← HIGH (packed?)" if entropy > 7.0 else ""
    print(f"  {section.Name.decode().strip(chr(0))}: {entropy:.2f}{flag}")

⚡Dynamic / Behavioral AnalysisMALWARE

⚠ Always run dynamic analysis in an ISOLATED sandbox VM. NEVER on production or connected systems.

Sandbox Setup Checklist

  • Isolated VM with no network access to production (host-only or isolated VLAN)
  • Snapshot taken BEFORE execution — roll back after each sample
  • Process Monitor (ProcMon), Process Hacker, Wireshark running before execution
  • Fake internet services: INetSim or FakeNet-NG to simulate C2 responses
  • Sysmon installed in VM for detailed telemetry
  • Disable Windows Defender (may quarantine before you capture behavior)
  • Set realistic computer/username (not "sandbox", "malware", "analysis")

Manual Dynamic Analysis Workflow

BASH
# Tools to run BEFORE executing the sample:
procmon.exe /BackingFile C:\analysis\procmon.pml /Quiet /Minimized
Start-Process wireshark -ArgumentList '-k -i Ethernet -w C:\analysis\capture.pcap'
Start-Process "Process Hacker"

# AFTER execution — collect artifacts:
# 1. ProcMon: filter by process name → look for:
#    - File system: new files, dropped payloads, config files
#    - Registry: Run keys, service keys, AppInit
#    - Network: TCP/UDP connections and DNS

# 2. Process Hacker: note:
#    - Injected processes (yellow highlight)
#    - New network connections
#    - Loaded DLLs vs baseline

# 3. Wireshark: filter for malware traffic:
wireshark_filter = "not arp and not icmp and not broadcast"
# Look for: HTTP POST (exfil/C2), DNS lookups, TLS to unknown IPs

🎯YARA RulesDETECTION

YARA Rule Structure

YARA
rule Detect_Emotet_Dropper {
    meta:
        author      = "SOC L2 - Your Name"
        date        = "2024-01-15"
        description = "Detects Emotet dropper based on string patterns and PE characteristics"
        reference   = "INC-XXXXX"
        severity    = "high"
        tlp         = "amber"

    strings:
        // C2 communication strings
        $s1 = "Content-Type: application/x-www-form-urlencoded" ascii
        $s2 = "/wp-admin/" ascii wide
        $s3 = "SoftwareUpdate" ascii wide nocase

        // Suspicious API imports
        $api1 = "VirtualAlloc" ascii
        $api2 = "CreateRemoteThread" ascii
        $api3 = "WriteProcessMemory" ascii

        // Hex pattern: XOR decryption loop
        $hex1 = { 8B 45 ?? 33 45 ?? 89 45 ?? 40 89 45 ?? }

        // Base64 encoded string (partial)
        $b64 = /[A-Za-z0-9+\/]{40,}={0,2}/

    condition:
        uint16(0) == 0x5A4D        // MZ header (PE file)
        and filesize < 5MB
        and (
            (2 of ($s*) and 2 of ($api*))
            or $hex1
            or (all of ($api*))
        )
}

Running YARA

BASH
# Scan single file
yara rule.yar sample.exe

# Scan directory recursively
yara -r rules/ /path/to/scan/

# Multiple rule files
yara rule1.yar rule2.yar sample.exe

# Scan running processes
yara -p 8 rules/ $(ls /proc/*/exe 2>/dev/null)

# Scan memory dump
yara rules/ memory.dmp

# With verbose output + all matches
yara -s rules/ sample.exe     # Show matched strings

# Compile rules for faster scanning
yarac rules/*.yar compiled.rules
yara compiled.rules /suspicious/

YARA Rule Best Practices

  • Use nocase for string matching where casing may vary
  • Use wide for Unicode strings in Windows binaries
  • Combine multiple weak indicators with and / 2 of to reduce false positives
  • Always test against clean file sets before deploying
  • Include filesize constraints to limit scan scope
  • Include magic bytes check: uint16(0) == 0x5A4D for PE files
  • Version and document all rules in meta section
  • Link rules to incident ticket and MITRE technique IDs in meta

Beaconing Detection — Statistical Approach

SPLUNK SPL
# Detect beaconing using standard deviation of connection intervals
index=network
| sort src_ip, dest_ip, _time
| streamstats window=20 range(_time) as time_range, stdev(_time) as time_stdev by src_ip, dest_ip
| eval jitter_ratio = time_stdev / (time_range/20)
| where jitter_ratio < 0.1 AND mvcount(split(dest_ip,",")) < 2
| stats count, avg(time_range) as avg_interval, avg(jitter_ratio) as avg_jitter by src_ip, dest_ip
| where count > 10
| sort avg_jitter

🏹Threat HuntingPROACTIVE

Threat hunting is proactive — you're looking for threats that evaded automated detection. Start with a hypothesis, not a specific alert.

Hunting Methodology

1
Form Hypothesis
Based on threat intel, recent incidents, or ATT&CK techniques. e.g., "Attackers are using WMI for persistence in our environment."
2
Identify Data Sources
What logs do you need? Process creation, registry, WMI activity, network flows? Confirm data availability.
3
Build Hunt Queries
Write SIEM queries to surface anomalies related to your hypothesis. Focus on rare or unusual patterns.
4
Analyze Results
Investigate outliers. Establish baselines. Eliminate known-good. Focus on unexplained activity.
5
Document Findings
Even negative hunts are valuable — document what you ruled out. If malicious found → create incident.
6
Create Detection Rule
Turn successful hunt into automated detection rule so it's caught automatically next time.

Hunt Queries — Advanced

SPLUNK SPL
# Hunt: Rare processes (low frequency = unusual = suspicious)
index=windows EventCode=4688
| stats count by NewProcessName
| where count < 5
| sort count

# Hunt: Processes running from suspicious paths
index=windows EventCode=4688
| eval suspicious_path = case(
    match(NewProcessName, "(?i)\\\\(temp|tmp|appdata|programdata|users\\\\public)\\\\.*\\.exe"), "YES",
    match(NewProcessName, "(?i)\\\\windows\\\\(fonts|help|cursors|media)\\\\.*\\.exe"), "YES",
    1=1, "NO")
| where suspicious_path = "YES"
| table _time, host, user, NewProcessName, CommandLine

# Hunt: Lateral movement via admin shares
index=windows EventCode=5140
| where ShareName IN ("\\\\*\\C$", "\\\\*\\ADMIN$", "\\\\*\\IPC$")
| where SubjectUserName != "SYSTEM" AND SubjectUserName != "LOCAL SERVICE"
| stats count by SubjectUserName, IpAddress, ShareName
| sort -count

# Hunt: Unusual PowerShell module imports
index=windows EventCode=4104
| regex ScriptBlockText="(?i)(Import-Module|ipmo)\s+(?!(Microsoft|posh|PS|AzureAD))"
| stats count, values(ScriptBlockText) by host, user
| sort -count

Eradication Checklist

  • All malware files identified and removed (or hosts rebuilt from clean image)

INCIDENT: Ransomware deployment on file server

WHY 1: Why was ransomware deployed?
  → Attacker had domain admin credentials and lateral movement capability.

WHY 2: Why did the attacker have domain admin credentials?
  → Domain admin credentials were stolen via LSASS dump on a workstation.

WHY 3: Why was LSASS dump possible?
  → Credential Guard was not enabled. Defender for Endpoint rule for LSASS
    protection was disabled on that OU.

WHY 4: Why was Credential Guard not enabled?
  → It was enabled in policy but an exception was made for a legacy app
    vendor requirement 18 months ago and never re-evaluated.

WHY 5: Why was the exception not re-evaluated?
  → No process exists to review security exceptions after initial approval.

ROOT CAUSE: Lack of security exception review process allowed an outdated
            exception to persist, creating a credential theft opportunity.

CORRECTIVE ACTIONS:
  - Immediate: Enable Credential Guard on all workstations (emergency change)
  - Short-term: Re-enable Defender LSASS protection rule
  - Long-term: Implement quarterly security exception review process
  - Strategic: Deploy PAM solution to reduce reliance on domain admin accounts

⬆️Escalation to L3ESCALATION

When to Escalate to L3

⬆ APT / nation-state indicators (sophisticated TTPs, zero-days, long dwell time)
⬆ Malware requiring reverse engineering beyond string analysis
⬆ Rootkit or bootkit suspected (OS-level compromise)
⬆ Novel attack technique not covered by existing runbooks
⬆ Legal / law enforcement involvement required
⬆ Large-scale breach with regulatory notification requirements
⬆ Incident duration > 72hrs without full containment

L3 Handoff Package

  • Full incident ticket with complete investigation notes
  • All collected evidence: memory dumps, disk images, PCAP files
  • Complete IOC list with enrichment results
  • Timeline of attack chain as reconstructed so far
  • All SIEM queries used and their results
  • Containment status — what is contained, what is not
  • MITRE ATT&CK techniques identified so far
  • Open questions and unknowns requiring deeper analysis
  • Current business impact and urgency
