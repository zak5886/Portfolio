Amass

Recon & OSINT

OWASP's attack-surface mapper — passive intel, active DNS, brute force, and graph visualization in one framework.

Amass isn't just a subdomain lister — it builds a graph database of every asset, relationship, and data source it touches (ASNs, netblocks, certs, WHOIS, DNS records). That graph is what separates it from a simple wordlist tool: you can query it later to answer questions like "which subdomains share this ASN" without re-scanning. It's maintained by the OWASP Amass project and is still one of the two or three tools (alongside subfinder and findomain) that professional bug-bounty hunters and red teamers reach for first during external recon.

✅ Fact-check & corrections
  • The subcommand list (enum, intel, viz, track, db) is accurate for Amass v3/v4.
  • -passive and -active are correctly described, but they're mutually exclusive in practice: -passive skips DNS resolution entirely (OSINT sources only, so results include some dead/unclaimed subdomains), while regular enum (no flag) already does active DNS resolution — -active on top of that additionally enables zone transfer attempts and reverse DNS sweeps, which is noisier and more likely to touch the target's infrastructure directly.
  • As of Amass v4, the legacy -config config.ini format was replaced by a YAML config (~/.config/amass/config.yaml) for API keys and data sources — the old .ini syntax shown in most older cheatsheets no longer works out of the box.

▸ Core commands, explained

Passive enumeration (OSINT only, zero direct contact) 
amass enum -passive -d example.com -o passive_subdomains.txt
whyPulls subdomains from certificate transparency logs, WHOIS, search engines, and other third-party sources without ever sending a packet to the target. Ideal for the very first recon pass before you've signed a scope-authorized testing window.
look forA list of hostnames — some may be stale (pointing to nothing, or to infrastructure the target no longer owns).
nextFeed the list into httpx or dnsx to filter for subdomains that actually resolve and respond over HTTP before spending time on them.
if stuckDomain has little public footprint, or your API keys aren't configured — passive sources are only as good as the keys you feed them.
Active enumeration with brute-forcing 
amass enum -active -brute -d example.com -w /usr/share/seclists/Discovery/DNS/subdomains-top1million-5000.txt
whyCombines passive sources with direct DNS brute-forcing to catch subdomains that were never indexed publicly (internal-only names, staging environments someone forgot to keep private).
look forA denser subdomain list, including ones only discoverable by guessing.
nextSort by whether each host resolves to a public or RFC1918 (internal) IP — internal-only hits are often the most interesting, since they leak internal naming conventions.
if stuckWordlist is too small, or the org uses random/hashed subdomain names that brute force can't guess.
Graph visualization 
amass viz -d3 -o results.html -d example.com
whyTurns the internal graph database into an interactive D3.js diagram, which is genuinely useful for client reports — it's the single visual most clients understand instantly.
look forAn HTML file with a force-directed graph of domains, IPs, and ASNs.
nextScreenshot it straight into your recon report; it communicates scope better than a wall of text ever will.
if stuckNo data was collected in a prior enum run for that domain — viz reads from the existing Amass database, it doesn't scan on its own.
Using API keys for deeper coverage 
amass enum -d example.com -config ~/.config/amass/config.yaml
whyFree passive sources (crt.sh, RapidDNS) only go so far. Adding keys for Shodan, VirusTotal, SecurityTrails, and Censys roughly doubles typical subdomain yield on a real engagement.
look forA noticeably larger subdomain list than the keyless run.
nextKeep a personal, versioned config.yaml template on your VPS so every new client engagement starts fully keyed.
if stuckFree-tier API rate limits exhausted — most of these services cap unauthenticated or free-tier daily lookups.

▸ How efficient pentesters actually use this today

Chain into httpx for a live-host shortlist (typical bug-bounty opener) 
amass enum -passive -d example.com -o subs.txt && cat subs.txt | httpx -silent -title -status-code -tech-detect -o live.txt
how it's usedThis is the real-world pattern almost every full-time bounty hunter runs first: passive recon feeds straight into httpx, which resolves each host, grabs the page title, HTTP status, and fingerprints the tech stack in one pass. You go from raw subdomain names to a triaged list of 'what's actually alive and worth looking at' in under a minute.
Diff scans over time to catch new attack surface 
amass enum -passive -d example.com -o today.txt
comm -13 <(sort yesterday.txt) <(sort today.txt) > new_hosts.txt
how it's usedAmass's own track subcommand does this natively, but most working pentesters just diff two dated output files with comm — simpler, scriptable, and easy to drop into a cron job for continuous recon on a retainer client.
📈 Current market usage

On a real engagement in 2026, Amass is rarely used alone — it's one leg of a recon stack alongside subfinder (faster, simpler passive-only) and dnsx/httpx (resolution and liveness). Efficient testers run Amass passively first for coverage, then reserve -active -brute for a specific subdomain that already looks interesting, since active mode is slow and noisy against a whole enterprise domain.

arp-scan

Network Discovery

Layer-2 host discovery that finds devices even when they're hiding from ICMP and TCP probes.

arp-scan works below IP entirely — it sends raw ARP requests and reads the replies, so it discovers every device on the local Ethernet/Wi-Fi segment regardless of host-based firewall rules, since ARP can't be blocked by an OS firewall the way ICMP or TCP can. This makes it the go-to first command the moment you get a foothold on an internal network segment during an on-site or OT/ICS assessment.

✅ Fact-check & corrections
  • All flags and syntax in the source sheet are accurate for the current arp-scan release.
  • One addition worth making explicit: arp-scan only works on the local broadcast domain (the segment your interface is physically/virtually attached to) — it cannot discover hosts across a router hop. That's the single most common reason new testers think it 'doesn't work.'

▸ Core commands, explained

Scan the local network 
sudo arp-scan --localnet
whyFires ARP 'who-has' requests for every address in the interface's connected subnet and lists everyone who answers.
look forIP, MAC address, and (very useful) the vendor OUI lookup — 'Dell', 'VMware', 'Raspberry Pi Foundation' tells you device type at a glance.
nextCross-reference vendor names against expected asset inventory; unexpected vendors (a random IoT device on a corporate VLAN) are worth flagging immediately.
if stuckNeeds sudo/root for raw sockets — if you get zero results, check privileges before assuming the network is empty.

▸ Options reference

FlagWhat it does
-l, --localnetScan the local network.
-I, --interface <iface>Specify the network interface.
-q, --quietIP and MAC only, no vendor lookup.
-g, --ignoredupsIgnore duplicate replies (common on VLAN-trunked interfaces).
-r, --retry <n>Retry attempts per host.
-t, --timeout <ms>Timeout per reply.
-v, --verboseVerbose output.

▸ How efficient pentesters actually use this today

Full engagement kickoff on a new internal segment 
sudo arp-scan -I eth0 --localnet | tee arp_results.txt
how it's usedOn internal/on-site engagements this is usually the literal first command run after plugging in — before nmap, before anything IP-based — because it's near-instant and unblockable by host firewalls. The saved file becomes the seed target list for every scan that follows.
Detecting rogue devices / unauthorized VLANs hopping 
sudo arp-scan -I eth0 --localnet -g
how it's usedDeduplicating replies matters on trunked interfaces where you might see the same MAC answer from multiple VLAN tags — a sign of VLAN hopping or a misconfigured trunk port, both worth flagging as findings on their own.
📈 Current market usage

Still the standard first move on any internal/physical engagement in 2026 — nothing has replaced it for layer-2 discovery. Efficient testers pair it with netdiscover as a passive cross-check and immediately pipe the IP list into a fast port scanner (rustscan/masscan) rather than running a slow full nmap sweep on unknown hosts.

Burp Suite

Web Application Testing

The industry-standard intercepting proxy — and increasingly, an AI-assisted testing platform.

Burp remains the center of gravity for web app pentesting: virtually every finding in a web report traces back to a Proxy history entry, a Repeater tab, or an Intruder attack. What's changed in the last two years is the depth of automation layered on top — Burp AI (natural-language-assisted request analysis), Bambda filters (inline Java-like filter/highlight scripting in the Proxy history), and a much more capable built-in scanner mean less time is spent on manual grunt work than a few years ago, though manual verification in Repeater is still non-negotiable before anything goes in a report.

✅ Fact-check & corrections
  • The five core modules (Proxy, Repeater, Intruder, Decoder, Comparer) and the four Intruder attack types (Sniper, Battering Ram, Pitchfork, Cluster Bomb) are all accurately described.
  • DOM Invader and Collaborator descriptions are accurate. Worth adding: DOM Invader now ships built into Burp's embedded Chromium browser (no separate extension install needed since Burp 2022.x+).
  • Missing from the original sheet: Bambda filters (custom inline filters/highlights in Proxy history, added 2023), the Organizer tab (issue triage/annotation workflow), and Burp AI (introduced 2025) which can suggest test steps and summarize a request/response pair — genuinely useful for junior testers but still requires manual confirmation since it can hallucinate vulnerability claims.

▸ Core commands, explained

Proxy — the foundation of everything 
Browser → 127.0.0.1:8080 (Burp's proxy listener) → intercept ON
whyEvery request/response your browser makes now passes through Burp first, letting you see, pause, and edit traffic before it reaches the server.
look forThe HTTP history sub-tab — look for auth tokens, hidden parameters, verbose error messages, and HTML comments.
nextRight-click anything interesting → Send to Repeater (manual testing) or Send to Intruder (automated fuzzing).
if stuckNo traffic showing up — check the browser is actually using 127.0.0.1:8080 as its proxy and that Burp's CA cert is installed for HTTPS interception.
Repeater — manual, iterative testing 
Right-click request → Send to Repeater → edit → Send
whyLets you tweak one parameter at a time and immediately see the effect, which is how you confirm a hypothesis (e.g. 'is this field vulnerable to SQLi') before automating anything.
look forDifferences in status code, response length, timing, or error text between your baseline and modified request.
nextOnce confirmed, script the same logic as a repeatable proof-of-concept for the report.
if stuckIdentical responses regardless of input usually means the parameter isn't processed server-side, or output is filtered/escaped.
Intruder — automated brute force and fuzzing 
Send to Intruder → mark § position § → choose attack type → load payload list → Start attack
whyAutomates sending hundreds or thousands of request variations — brute-forcing logins, fuzzing parameters, testing an ID range for IDOR.
look forSort results by response length or status code; a login page's failed attempts are usually uniform, so an outlier row is your hit.
nextConfirm the outlier manually in Repeater before reporting it — Intruder gives you leads, not final proof.
if stuckAll responses identical — the app may be rate-limiting, WAF-blocking, or genuinely not vulnerable at that position.

▸ Options reference

FlagWhat it does
SniperOne payload set, one position at a time — good for single-parameter fuzzing.

▸ How efficient pentesters actually use this today

Bambda filter to isolate JWT-bearing requests in a huge history 
// Proxy → HTTP history → Filter → Bambda editor
return requestResponse.request().headerValue("Authorization") != null
  && requestResponse.request().headerValue("Authorization").contains("Bearer");
how it's usedOn a large SPA with thousands of history entries, Bambda filters (Burp's inline scripting filter, added in 2023.x) let you write a one-line condition instead of scrolling manually. This specific filter is one of the most-used patterns for API/JWT-heavy modern web apps.
Turbo Intruder for high-volume race-condition testing 
# BApp Store → install Turbo Intruder
# Extender tab → Turbo Intruder → paste Python attack script → Attack
engine = RequestEngine(endpoint=target, concurrentConnections=30, engine=Engine.BURP2)
for i in range(20):
    engine.queue(target.req, gate='race1')
engine.openGate('race1')
how it's usedStandard Intruder is throttled by design and can't reliably fire dozens of requests within the same millisecond — which is exactly what's needed to exploit race conditions (double-spend coupon codes, TOCTOU issues in balance transfers). Turbo Intruder's request-gating pattern shown here is the current standard technique used to demonstrate race-condition findings in modern bug bounty reports.
Param Miner for hidden/cache-poisoning parameters 
# BApp Store → install Param Miner
# Right-click request → Guess params → Guess headers / Guess GET/POST parameters
how it's usedParam Miner brute-forces hidden parameter and header names against a request and is the tool most testers reach for when hunting web-cache-poisoning bugs — still one of the highest-paying bug classes on bounty platforms.
📈 Current market usage

Burp Pro (or the free Community edition for manual-only work) is still non-negotiable for web pentesting in 2026. Efficient testers lean heavily on the BApp Store — Param Miner, Turbo Intruder, Autorize (access-control testing), and Logger++ round out a modern setup — and treat Burp's built-in AI-assisted scanning as a triage aid, never as a replacement for manually walking Repeater through every finding before it goes in a report.

CrackMapExec / NetExec

Active Directory

AD swiss-army knife for spraying, enumerating, and executing across an entire domain at once.

This is the single most important correction across the whole batch: CrackMapExec (CME) was archived by its maintainer in 2023 and is no longer developed. The actively maintained continuation is NetExec (nxc), built by much of the same community, using an almost identical command syntax — most cme ... commands work by swapping in nxc ... unchanged. Anyone learning this tool today should install and practice with NetExec, not the archived CME package, even though the muscle memory and module names carry straight over.

✅ Fact-check & corrections
  • Correction: CrackMapExec's GitHub repository was archived (read-only) in 2023. Kali and other current distros now ship netexec as the package name; the binary is invoked as nxc.
  • All command syntax below is shown in both forms — historic cme and current nxc — since the flags are functionally identical.
  • The listed modules (gpp_password, mimikatz, spider_plus, bloodhound, lsassy, reg) all exist in NetExec too, though a few module names have shifted slightly between versions — always run nxc smb -L to list modules actually available in your installed version.
  • --gen-relay-list is a real flag, but it generates a list of SMB-signing-disabled hosts for use with ntlmrelayx.py — it does not save credentials to the internal database as the original sheet implied. Credentials are stored automatically in the CME/NetExec workspace database on every successful login, with no flag needed.

▸ Core commands, explained

Password spraying across a subnet 
nxc smb 10.10.10.0/24 -u users.txt -p 'Summer2026!'
whyTests one password against many usernames across every live host — the standard way to find one weak account in a large environment without triggering per-account lockout (since each account only gets one attempt).
look forA (Pwned!) tag next to a host/username combo indicates a valid login.
nextImmediately re-run enumeration modules (--shares, -M bloodhound) using that new credential.
if stuckNo hits — try the inverse (one known username, many common passwords) or check the domain's password/lockout policy first with nxc smb $IP -u '' -p '' --pass-pol.
Share enumeration 
nxc smb $IP -u zak -p zak123 --shares
whyFinds every file share the current credential can see and what access level it has.
look forShares flagged READ or WRITE beyond the defaults (C$, ADMIN$, IPC$, SYSVOL, NETLOGON).
nextPoint -M spider_plus at readable shares to search their contents automatically instead of browsing manually.
if stuckAccess denied everywhere — the account may have no meaningful share permissions, which is itself worth noting.
Command execution 
nxc smb $IP -u zak -p zak123 -x "whoami /all"
whyRuns a command remotely once you have valid credentials, without needing a full interactive shell — fast way to confirm privilege level across many hosts at once.
look forCommand output returned directly in the terminal.
nextIf the account has local admin, escalate to a full shell (psexec.py, evil-winrm) or dump credentials with -M lsassy.
if stuckAccess denied — account isn't a local admin on that host, which restricts you to lower-privilege actions like RID cycling or share enumeration.
Pass-the-Hash 
nxc smb $IP -u zak -H <ntlm_hash> --shares
whyAuthenticates using a captured NTLM hash instead of a plaintext password — essential once you've dumped hashes via secretsdump or Mimikatz.
look forSame (Pwned!) success indicator as password auth.
nextHash reuse across hosts (local admin password reuse) is one of the highest-value findings in an AD assessment — spray the hash across the whole subnet, not just one host.
if stuckHash rejected — double check it's the NT hash, not the LM hash half, and that you haven't accidentally included the LM portion.

▸ Options reference

FlagWhat it does
-M gpp_passwordFinds credentials left in Group Policy Preferences XML files.
-M mimikatzDumps in-memory credentials via Mimikatz.
-M spider_plusRecursively searches accessible shares for sensitive filenames/content.
-M bloodhoundCollects AD relationship data for BloodHound analysis.
-M lsassyDumps LSASS memory remotely without dropping a binary to disk.
-M regReads/writes registry keys and values remotely.

▸ How efficient pentesters actually use this today

Full loot sweep in one line (typical AD-assessment day-one workflow) 
nxc smb $IP -u zak -p zak123 --shares && nxc smb $IP -u zak -p zak123 -M spider_plus -M gpp_password && nxc ldap $IP -u zak -p zak123 --bloodhound --collection All
how it's usedChaining these three calls is close to the actual muscle-memory workflow of an experienced AD tester on day one of an internal assessment: confirm access, sweep shares for low-hanging leaked secrets, then immediately pull full BloodHound collection data so path-finding can start in parallel while manual enumeration continues.
Local-admin password reuse check across the whole domain 
nxc smb domain_hosts.txt -u administrator -H <ntlm_hash> --shares 2>&1 | grep Pwned
how it's usedOnce you've cracked or dumped one local admin hash, spraying it across every known host in the domain is the fastest way to reveal 'gold image' password reuse — one of the most common and most damaging AD misconfigurations, and usually a headline finding in the final report.
📈 Current market usage

NetExec (nxc) is what's actually installed on Kali by default now and what's used in real engagements — treat CrackMapExec as legacy naming you'll still see referenced in older writeups and OSCP/CPTS material, but install and drill on NetExec. The workflow logic (spray → enumerate shares → dump credentials → pivot) hasn't changed, only the binary name and a handful of module tweaks.

dig

DNS Reconnaissance

The precision instrument for DNS — every subdomain enumeration tool eventually calls something like this under the hood.

dig is the tool you reach for once amass/subfinder has given you a list, when you need to answer a specific, surgical question: what MX records does this domain have right now, does this subdomain still resolve, is this DNS server willing to hand over a full zone. It's also the fastest way to sanity-check findings from automated tools before writing them into a report.

✅ Fact-check & corrections
  • All record types, flags, and syntax shown are accurate and current.
  • Worth noting: ANY queries are increasingly refused or rate-limited by modern authoritative servers (RFC 8482 recommends this) as an anti-amplification-DDoS measure, so a real assessment today usually queries record types individually (A, AAAA, MX, TXT, NS) rather than relying on ANY returning everything.

▸ Core commands, explained

Basic lookup 
dig example.com
whyQuick sanity check of a domain's A record and general DNS health, including the full response with query/answer/authority sections.
look forThe ANSWER SECTION for the resolved IP; the query time and SERVER line confirm which resolver actually answered.
nextCross-reference the IP against known cloud provider ranges (AWS, Azure, Cloudflare) to understand hosting.
if stuckNXDOMAIN means the domain doesn't exist or isn't delegated yet.
Specific record types 
dig example.com MX
dig example.com TXT
dig example.com NS
whyEach record type answers a different recon question: MX reveals the mail provider (Google Workspace vs O365 vs self-hosted — relevant for phishing infra choices), TXT often leaks SPF/DKIM policy and sometimes verification tokens for other services (which reveal what SaaS tools the org uses), NS shows who hosts their DNS.
look forTXT records mentioning specific SaaS platforms (google-site-verification, docusign, atlassian-domain-verification) are a quiet way to fingerprint the org's tool stack.
nextFeed discovered SaaS platform names into your OSINT notes — they're useful later for pretexting and for guessing what auth provider (SSO) the target uses.
if stuckEmpty answer for a record type just means that type isn't configured, not an error.

▸ Options reference

FlagWhat it does
+shortJust the answer, no headers/footers.
+noall +answerOnly the answer section.
+traceFull delegation path from root servers down.
-x <ip>Reverse lookup (PTR record).
@<server>Query a specific DNS server directly.

▸ How efficient pentesters actually use this today

Zone transfer test (the single most valuable dig command in recon) 
dig axfr @ns1.example.com example.com
how it's usedTests whether the authoritative nameserver will hand over the entire zone file to anyone who asks — a severe misconfiguration that, when it works, instantly reveals every internal and external hostname the org has ever configured. Still found occasionally on real engagements, especially against older or self-managed BIND servers, and is an easy high-severity finding when it hits.
Bulk resolution from a subdomain list 
for sub in $(cat subs.txt); do dig +short "$sub" A; done
how it's usedA quick one-liner to batch-resolve a subdomain list from amass/subfinder without needing a heavier tool like dnsx installed — useful when you're working from a minimal toolbox on a locked-down jump host.
📈 Current market usage

dig stays relevant forever because it's the raw primitive everything else is built on. In current workflows it's used less for bulk enumeration (that's massdns/dnsx/puredns territory now, which are far faster at scale) and more for targeted verification — confirming a single finding, testing one nameserver for a zone transfer, or debugging why an automated tool returned something unexpected.

dirb

Web Content Discovery

One of the original directory brute-forcers — mostly of historical and educational value today.

dirb pioneered dictionary-based web content discovery, but it's single-threaded and noticeably slower than its modern replacements. It still ships on Kali and still works fine for a quick one-off scan, but almost no working pentester makes it their primary tool anymore.

✅ Fact-check & corrections
  • All flags and syntax are correct and current.
  • Important market-reality flag: dirb has effectively been superseded by gobuster, ffuf, and feroxbuster, all of which are multi-threaded (dirb is single-threaded by design) and an order of magnitude faster on the same wordlist. Most current course material (including HTB's own CPTS track) still teaches dirb first because its defaults are forgiving and its output is easy to read, but production engagements almost always use one of the faster three tools instead.

▸ Core commands, explained

Basic scan 
dirb http://$IP
whyRuns dirb's own default wordlist (common.txt) against the target, checking each guessed path for a non-404 response.
look forPaths like /admin, /backup, /config.php returning 200, 301, or 403 (403 still confirms the path exists, just access is blocked).
nextManually browse anything interesting; 403 results are worth a second look with a different HTTP method or a trailing slash, since some misconfigurations only block GET.
if stuckdirb's bundled wordlist is small — a clean scan doesn't mean the server has no hidden content, only that this specific wordlist found nothing.

▸ Options reference

FlagWhat it does
-o <file>Save output.
-w <wordlist>Use a custom wordlist.
-X <ext>Append extensions to wordlist entries.
-rDisable recursive scanning.
-SSilent mode.
-z <ms>Delay between requests.
-p <proxy>Route through a proxy.

▸ How efficient pentesters actually use this today

Quick triage scan before switching to feroxbuster 
dirb http://$IP -S -o dirb_quick.txt &
how it's usedSome testers still background a fast dirb pass as a first-minute sanity check while setting up a proper feroxbuster/ffuf scan with a larger wordlist — it costs nothing to run in parallel and occasionally catches something obvious before the main scan even finishes starting up.
📈 Current market usage

Learn it because it's still in the CPTS/OSCP curriculum and every walkthrough references it, but for actual paid engagement work, default to feroxbuster or ffuf — both covered later in this guide — since the speed difference on a large wordlist against a slow target is the difference between a five-minute scan and a five-hour one.

dnsrecon

DNS Reconnaissance

Python-based DNS enumeration that bundles zone-transfer testing, brute forcing, and reverse lookups into one tool.

dnsrecon sits between dig (surgical, single-query) and amass (broad, multi-source graph building) — it's a good all-in-one when you want standard record enumeration, a zone-transfer attempt, and a brute-force pass without switching tools. It's less actively developed than amass but its output formats (XML/CSV/JSON) make it easy to feed into other tooling or report templates.

✅ Fact-check & corrections
  • All enumeration types (std, axfr, brt, rvl, srv, bing, crt) and flags are accurate.
  • Note that the bing source has become unreliable over the past couple of years as Bing has tightened anti-scraping measures — expect it to return little or nothing without a Bing API key configured; crt (certificate transparency) is now the more reliable free source in this tool.

▸ Core commands, explained

Standard enumeration 
dnsrecon -d example.com
whyRuns a full standard sweep — SOA, NS, A, AAAA, MX, SRV, plus a zone-transfer attempt against each nameserver automatically.
look forA structured list of every standard record type found.
nextNote the SOA serial and refresh/retry/expire values — unusually long TTLs can hint at infrequently updated legacy infrastructure.
if stuckDomain has minimal DNS footprint or the server refused all queries.
Zone transfer attempt 
dnsrecon -d example.com -t axfr
whyExplicitly tests every NS record for a zone transfer misconfiguration.
look forA full record dump if vulnerable — otherwise a clear 'transfer failed' message per server.
nextIf successful, this alone is often a critical finding — write it up immediately with the full record dump as evidence.
if stuckModern DNS servers reject AXFR from non-whitelisted IPs by default, so failure here is the expected, secure outcome.

▸ Options reference

FlagWhat it does
-n <server>Specify a DNS server.
-t <type>Enumeration type: std, axfr, brt, rvl, srv, bing, crt.
-D <file>Dictionary file for brute forcing.
-r <range>IP range for reverse lookups.
--threads <n>Thread count.
-j <file>JSON output.

▸ How efficient pentesters actually use this today

Hydra is still installed and used, but for anything Active-Directory-adjacent (SMB, WinRM, RDP, LDAP), efficient testers increasingly reach for NetExec's built-in, lockout-aware password spraying instead, since it natively tracks and respects the domain's actual lockout policy rather than relying on manual timing guesses. Hydra remains the better choice for non-AD services (raw SSH, FTP, custom web forms) where that lockout-awareness isn't relevant.

Impacket

Active Directory

The Python library and script collection underpinning most modern AD attack tooling.

Impacket isn't one tool but a toolkit of individual scripts, each implementing a specific Windows/AD protocol interaction from scratch in Python — which is exactly why it's so widely used: no dependency on having Windows tools available, full control over the raw protocol exchange, and it's the reference " implementation most other AD attack tools (like NetExec) build on top of internally.

✅ Fact-check & corrections
  • GetUserSPNs.py, GetNPUsers.py, secretsdump.py, psexec.py, smbserver.py, ntlmrelayx.py, ticketer.py, wmiexec.py, atexec.py, and mssqlclient.py are all real, current Impacket scripts and the syntax shown for each is accurate.
  • Correction: getPac.py does not exist as a standalone Impacket script. The actual scripts for PAC/ticket work are getTGT.py (request and save a TGT to a ccache file), getST.py (request a service ticket, used for S4U2Self/S4U2Proxy delegation abuse), and describeTicket.py (parses and pretty-prints an existing ccache/kirbi ticket's PAC contents) — the correction is to use describeTicket.py for the PAC-inspection use case the original entry was describing.
  • Correction: klist.py is not an Impacket script either — klist is a native Windows (and Linux MIT-Kerberos) command for listing cached tickets, unrelated to the Impacket project. To view tickets on Linux with Impacket-adjacent tooling, use KRB5CCNAME=ticket.ccache klist (native klist against an Impacket-generated ccache file) rather than a nonexistent Impacket script.
  • Correction: a standalone mimikatz.py does not exist in Impacket. Credential dumping equivalent to Mimikatz functionality in the Impacket ecosystem is done via secretsdump.py (remote, no agent needed) — there is no direct Python reimplementation of Mimikatz's full feature set inside Impacket itself.

John the Ripper

Password Cracking

The flexible, format-aware password cracker — still the right tool when hashcat's GPU speed isn't the deciding factor.

John's strength over hashcat isn't raw speed (hashcat wins that on GPU-friendly hash types) — it's breadth of format auto-detection, the *2john family of pre-processing scripts that convert obscure file formats into crackable hashes, and a more forgiving mask/rule syntax for CPU-based cracking. In practice most testers keep both installed and pick based on hash type and available hardware.

✅ Fact-check & corrections
  • All commands, rule syntax, and mode descriptions are accurate for current John the Ripper (Jumbo) builds.
  • Worth clarifying: most current Kali installs ship 'John the Ripper Jumbo', a community-extended fork with far more format support and the full *2john script collection — the vanilla upstream John is comparatively bare.

▸ Core commands, explained

Wordlist attack 
john --wordlist=/usr/share/wordlists/rockyou.txt hashes.txt
whyCompares every hash against every word in the list — the standard first attempt, since real-world passwords are disproportionately dictionary-based or close variants.
look forTerminal output announcing each cracked password as it's found.
nextRun john --show hashes.txt to see the full cracked list once the run finishes or is interrupted.
if stuckNo hits — the hash format may not have been auto-detected correctly; specify it explicitly with --format.
Rule-based mutation attack 
john --wordlist=rockyou.txt --rules=KoreLogic hashes.txt
whyApplies systematic mutations (capitalization, leetspeak substitutions, appended digits/years) to every wordlist entry, covering the enormous space of 'dictionary word + slight variation' passwords real users actually pick.
look forA meaningfully higher crack rate than the plain wordlist run.
nextIf KoreLogic doesn't yield much more, try the built-in 'best64' rule set (from hashcat, importable into John) for a different mutation strategy.
if stuckPassword policy likely enforces enough complexity that simple mutations of dictionary words don't cover it — move to mask mode with a policy-informed pattern.

📈 Current market usage

Efficient testers use John and hashcat together rather than picking one: John for its unmatched breadth of *2john format conversion and CPU-friendly flexible rule syntax, hashcat for raw GPU-accelerated speed on high-value hash types (NTLM, Kerberos tickets) where cracking millions of candidates per second actually matters.

LinEnum.sh

Linux Privilege Escalation

An early, still-functional Linux enumeration script — largely superseded by linpeas.sh in current practice.

LinEnum was one of the original one-shot Linux privesc enumeration scripts, and the categories it checks (kernel/OS version, SUID/SGID binaries, writable files, cron jobs, sudo rules) are still exactly the right things to look at. What's changed is that its successor, linpeas.sh, checks a superset of the same things with color-coded output that highlights likely-exploitable findings automatically, which is why it's become the default choice on almost every current engagement.

✅ Fact-check & corrections
  • All usage instructions and the 'key information to look for' list are accurate and remain good general privilege-escalation guidance regardless of which specific script you run.
  • Market-reality note: LinEnum has had minimal active development in recent years compared to linpeas.sh (part of the PEASS-ng suite), which checks a broader set of misconfigurations, includes color-coded severity highlighting (bright yellow/red flags likely-exploitable findings automatically instead of you having to read every line), and is updated far more frequently to catch newly disclosed privesc techniques. LinEnum is still fine to know and occasionally useful when linpeas is flagged/blocked by AV and a smaller, less signatured script is needed, but it shouldn't be your default choice in 2026.

lse.sh

Linux Privilege Escalation

Linux Smart Enumeration — actively maintained, verbosity-tiered, and genuinely still in regular use.

lse.sh's defining feature is its three-tier verbosity system: level 0 shows only the findings the author considers highly likely to be directly exploitable, level 1 adds interesting-but-not-certain findings, and level 2 dumps everything. That triage-by-default design is what keeps it in regular rotation alongside linpeas rather than being fully replaced by it — less noise to wade through on a first pass.
